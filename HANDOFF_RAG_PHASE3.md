# HANDOFF: RAG Layer — Phase 3 (ChromaDB Setup + Hybrid Retrieval)

## Scope

This phase turns the already-approved 45-chunk MITRE ATT&CK knowledge base (Phase 1: `data/knowledge_base/mitre_techniques.json`; Phase 2: the chunking plan — 11 description + 11 detection + 23 deduplicated mitigation chunks, now documented in `docs/rag_chunking_plan.md`) into a working, queryable hybrid retrieval system: a ChromaDB collection populated with those 45 chunks, embedded with `BAAI/bge-m3`, retrievable via a BM25 + dense-vector hybrid search, and evaluated for retrieval precision@3 against CICIDS-2017's **14 attack categories** that have a known `technique_id` in `config/mitre_mapping.csv` (`BENIGN` is the 15th `Label` value but maps to no `technique_id` and is excluded from the precision test, not silently dropped).

**This phase is explicitly NOT:**
- Not `enrich.py` — this phase indexes the *static* `data/knowledge_base/mitre_techniques.json` snapshot, not a live OpenCTI GraphQL/pycti feed. `enrich.py` (the Kafka consumer that queries OpenCTI for IoC match + graph walk) remains unbuilt and out of scope here.
- Not the LLM explanation layer — do not wire this retrieval module into a Typhoon2.1 prompt or produce Thai JSON output. That is a separate, later phase.
- Not a retrain of any ML ensemble member (Isolation Forest / Random Forest / Autoencoder / Fusion Layer) — none of those files should be touched.
- Not a rebuild of Phase 1 or Phase 2. Do not regenerate `data/knowledge_base/mitre_techniques.json` or re-litigate the chunk boundaries — treat the 45-chunk plan in `docs/rag_chunking_plan.md` as fixed input. If you find a reason the plan is wrong, stop and ask rather than silently redesigning it.

## Conventions that must be followed

- **Config-driven, not hardcoded.** Read `CHROMA_HOST`, `CHROMA_PORT`, `CHROMA_COLLECTION`, `EMBED_MODEL`, `RAG_TOP_K`, `RAG_REINDEX_HOURS` from the root `.env` (e.g. `python-dotenv` or `os.environ`), matching how every other `.env`-driven stack in this repo works. `.env` already has the correct values (`CHROMA_COLLECTION=mitre_attack_kb`, `EMBED_MODEL=BAAI/bge-m3`) — don't hardcode them separately in code.
- **Chunk metadata is mandatory, not optional.** Every chunk indexed into ChromaDB must carry at least `technique_id` and `chunk_type` (`description` / `detection` / `mitigation`) as metadata; deduplicated mitigation chunks must also carry `mitigation_id` **and the full list of `technique_id`s they apply to** (per `docs/rag_chunking_plan.md` — a shared mitigation like `M1037` applies to 4 techniques and must remain retrievable against all of them, not just the one it was first seen under).
- **Sub-technique stubs are not chunkable content.** Per the investigation in `docs/rag_chunking_plan.md`: only the 11 top-level keys of `mitre_techniques.json`'s `techniques` dict have real `description`/`detection`/`mitigations` text. Some of those 11 (`T1059`, `T1498`, `T1595`, `T1110`) also list a `sub_techniques` array of bare `{technique_id, name}` stubs with no text of their own (e.g. `T1059.001` PowerShell) — iterate only over the 11 top-level entries for chunking; treat `sub_techniques` as read-only reference metadata and never attempt to derive a chunk from a stub entry. Exception already accounted for: `T1110.001` is both a stub under `T1110` *and* its own full top-level entry (intentional — `config/mitre_mapping.csv` maps FTP-/SSH-Patator to the specific `T1110.001`, distinct from `T1110` generic Brute Force used for Web Attack - Brute Force) — chunk both independently, they are not duplicates.
- **No leakage between the query set and the index.** `config/mitre_mapping.csv`'s attack-category → `technique_id` mappings are the evaluation query set only — never use them to influence chunking, embedding, or indexing. This mirrors this project's standing fit-on-train-only / no-leakage discipline, applied here to retrieval instead of ML training.
- **Decisions get a config sidecar, not just code.** The LangChain-vs-custom hybrid-retrieval decision — and its reasoning — must be written to `models/rag_retrieval_config.json` (chosen approach, embedding model, `top_k`, BM25/dense weighting if applicable, collection name, chunk counts), following the `models/fusion_config.json` precedent. Do not leave the reasoning only in a notebook cell or code comment.
- **Report per-category, not blended.** Precision@3 must be reported per attack category (14 rows, one per CICIDS-2017 attack `Label` with a known `technique_id`), not as a single averaged number — this repo's established convention (see Isolation Forest/Random Forest/Autoencoder LOAO results) is that per-category detail is where the real signal is.
- **Dependency placement**: confirm before installing whether `chromadb`/`langchain` (if chosen)/`sentence-transformers` or equivalent `bge-m3` embedding runtime belong in `pyproject.toml` (`.venv`, currently `ipykernel`-only) or are meant for the system Anaconda Python that already runs every other real pipeline script/notebook in this repo (see CLAUDE.md's Commands section) — this is a repo-wide ambiguity CLAUDE.md itself flags, not something specific to this phase.
- **Never print or commit `.env` contents** — it contains `OPENCTI_TOKEN`.

- A running ChromaDB collection named `mitre_attack_kb` (from `.env`'s `CHROMA_COLLECTION`) containing exactly 45 chunks built from `data/knowledge_base/mitre_techniques.json`, each with `technique_id`/`chunk_type`(/`mitigation_id`) metadata.

- A precision@3 evaluation script or notebook that queries the retrieval module using `config/mitre_mapping.csv`'s CICIDS-2017 attack categories as ground truth.
- `reports/rag_retrieval_precision_at_3.csv` — per-category precision@3 results (14 rows) plus an aggregate row, following this repo's existing `reports/*_val_metrics.csv` shape.
- A plain-text or CSV run report (e.g. `reports/rag_layer_report.txt`) summarizing what was indexed, chunk counts, and the retrieval strategy decision — following the `reports/*_report.txt` convention.
