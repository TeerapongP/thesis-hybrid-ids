## Conventions that must be followed

### RabbitMQ: reuse decision — investigated, decided, and implemented (2026-07-15)
The diagram already says `"RabbitMQ (reuse opencti-rabbitmq)"` and `notification/.env` was already wired to `opencti-rabbitmq`'s host/port/credentials with a dedicated `RABBITMQ_EXCHANGE=soc.alerts`. Investigated for this handoff: was exchange-level separation on the *default* vhost enough, or did SOC alert traffic need to be isolated further from OpenCTI's own internal AMQP traffic (OpenCTI's platform and worker containers use this same RabbitMQ instance for their own async job queue, per `opencti/docker-compose.yml`'s `RABBITMQ__*` environment block on `opencti-platform`)?

**Decided and implemented: reuse the broker instance (no second RabbitMQ container was stood up), isolated on a dedicated `soc` vhost.** Reasoning (unchanged from the original recommendation, now executed):
- Standing up a second RabbitMQ instance would duplicate infrastructure `CLAUDE.md`'s own repo-wide bias explicitly argues against (see `src/rag/rag_retrieval.py`'s docstring reasoning for avoiding LangChain, cited approvingly in `HANDOFF_LLM_LAYER.md` §"Backend choice"). The broker was already running, already reachable from both host and `soc_shared`-attached containers (confirmed per Required Reading #7), and already had credentials provisioned.
- `RABBITMQ_URL`'s previous trailing `/` (no vhost segment) pointed SOC traffic at RabbitMQ's default vhost, the same one OpenCTI's platform/worker use for their own queues — exchange-name separation alone (`soc.alerts` vs. OpenCTI's internal exchanges) avoids message *collision* but not administrative isolation.

**What was actually done, against the live `opencti-opencti-rabbitmq-1` container:**
```
docker exec opencti-opencti-rabbitmq-1 rabbitmqctl add_vhost soc
docker exec opencti-opencti-rabbitmq-1 rabbitmqctl set_permissions -p soc opencti ".*" ".*" ".*"
```
Verified via `rabbitmqctl list_vhosts` (now lists `soc` alongside `/`) and `rabbitmqctl list_permissions -p soc` (confirms the existing `opencti` user has full configure/write/read on the new vhost — no new RabbitMQ user was created, the already-provisioned `opencti` credentials were reused, just scoped to the new vhost too). `notification/.env`'s `RABBITMQ_URL`/`RABBITMQ_DOCKER_URL` were updated from `.../5672/` to `.../5672/soc`, and a new `RABBITMQ_VHOST=soc` key was added for code that needs the vhost name independent of the connection URL. The change is commented in-file with a pointer back to this section.

**Exchange type**: the diagram says `"topic routing"`. Declare `soc.alerts` as a **durable topic exchange** on the `soc` vhost, with routing keys that let LINE/Gmail/InfluxDB-writer consumers each bind only to what they need, e.g. `alert.HIGH`, `alert.MEDIUM`, `alert.LOW` for the three priority tiers (dispatcher publishes; LINE sender binds to `alert.HIGH` only, Gmail sender binds to `alert.MEDIUM`+`alert.LOW`, the InfluxDB/metrics writer binds to `alert.#` for all three). Exact routing-key scheme is still this phase's implementation-time call to finalize — document it in the config sidecar — but the topic-exchange-with-priority-suffixed-keys shape is not optional, it's what the diagram's "topic routing" phrase specifies and what makes the HIGH/MEDIUM/LOW fan-out actually work without every consumer filtering client-side. (Declaring the exchange itself, e.g. via `pika`'s `exchange_declare`, is left to `alert_dispatcher.py`'s implementation — only the vhost/permissions were provisioned ahead of time, not the exchange, since exchange declaration is idiomatically done by the publishing application at connect time, not via `rabbitmqctl`.)

### Kibana: reuse the cluster, not the index — resolved and fixed (2026-07-15)
The diagram's `"index: reuse opencti-elasticsearch"` must be read as **reuse the Elasticsearch cluster/service**, not literally write into OpenCTI's own entity/relationship indices. OpenCTI's internal indices (`opencti_*`, holding STIX objects) are a completely different data model from this phase's alert/log records; mixing them would corrupt OpenCTI's own search behavior and doesn't match what's actually provisioned anyway (Grafana's `Elasticsearch-SOC` datasource is already scoped to a separate, SOC-specific index name, confirmed per Required Reading #8–9).

**Naming mismatch — found, root-caused, and fixed.** Logstash (`observability/logstash/pipeline/soc.conf`) writes to `soc-<kafka-topic>-YYYY.MM.dd` (four rolling daily indices: `soc-pa5220.raw-*`, `soc-pa5220.enriched-*`, `soc-pa5220.features-*`, `soc-pa5220.ml_output-*`), but `ELASTIC_ALERT_INDEX` was set to the literal, non-wildcarded `soc-alerts` — no matching Logstash output, nothing wrote to it. This handoff's first draft offered two options ((a) extend Logstash's Kafka topics to cover `pa5220.llm_output`, or (b) have `alert_dispatcher.py` write directly to Elasticsearch) without picking one. **Resolved as (b), on direct evidence, not a coin flip**: fixing the Kibana ndjson's missing index-pattern (Required Reading #5) required actually reading the saved-object export closely, and its search object's own `description` already read `"Latest SOC alert events from soc-alerts*"` with a `columns` list (`priority, risk_score, source_ip, dst_port, anomaly_type, mitre_tactic, model_used, response_ms, alert_id`) matching an *assembled final alert record* — not a raw `pa5220.llm_output` Kafka message, and not any of the 4 existing `pa5220.*` topics either. The dashboard was designed around `alert_dispatcher.py` writing its own finished record straight to Elasticsearch all along; option (a) would have built a redundant, incomplete path nothing actually needs (see Required Reading #6 for the full reasoning on why Logstash's topic list stays as-is).

### InfluxDB schema is not negotiable — it already exists
`grafana/dashboards/soc-overview.json` is a real, already-provisioned dashboard (Required Reading #4) whose 5 panels' Flux queries fully specify the schema `alert_dispatcher.py`'s InfluxDB writer must produce. Do not invent a different schema — write exactly this:

- **Measurement**: `soc_alert` (one point per dispatched alert).
- **Tags** (queried via `r.priority`, and via `pivot(rowKey: [...])`/`keep(columns: [...])` in the "Latest Alerts" table panel, which names: `alert_id`, `source_ip`, `dst_port`, `priority`, `anomaly_type`, `mitre_tactic`) — these must be written as InfluxDB **tags** (indexed, used for `group()`/`filter()`), not fields.
- **Fields**: `risk_score` (numeric, dashboard's `Risk Score Trend`/`Latest Alerts` panels treat it as 0–100, `fieldConfig.defaults.min/max: 0/100` — confirms this is the `CLAUDE.md`-described "0–100 risk score," **not** `fused_score`'s native `[0,1]` range; the dispatcher must compute `risk_score = round(fused_score * 100)` before writing, since neither `fuse()` nor `explain_alert(...)` returns a pre-scaled 0–100 value per Required Reading #2), `response_ms` (numeric, ms). **`faithfulness_score` is deliberately not a `soc_alert` field** — metric production is paused pending a real definition.
- **Timestamp**: the point's own `_time`, i.e. the alert's timestamp — reuse the same `timestamp` field the alert context already carries (per `HANDOFF_LLM_LAYER.md`'s few-shot example, ISO-8601 with `+07:00` offset), don't let the InfluxDB client default to "now" if the alert was processed with any lag.

Write one point per alert, all fields+tags in the single `soc_alert` measurement — the dashboard's queries all filter on `r._measurement == "soc_alert"` and expect every tag/field to coexist on the same point (the "Latest Alerts" panel's `pivot()` call requires this).
