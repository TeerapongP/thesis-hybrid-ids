THREE DEFECTS THE RUN FOUND
---------------------------
1. THE SUMMARY CRASHED AFTER SENDING.  render_summary subscripted d["status"], but a real
   dispatch_alert receipt has no top-level "status" -- it carries alert_id and priority plus
   one status per sink. Only the dry-run shapes this module builds itself have that key, so
   the default path could never hit it. Every --dispatch run therefore raised KeyError
   *after* the alert had been published and the LINE message sent: the work succeeded and
   the operator saw a traceback. Fixed to .get(); a test now asserts the real receipt shape
   renders, using the exact receipt from this run.

2. RABBITMQ'S `soc` VHOST IS CREATED BY NOTHING IN THE REPO.  A first dispatch failed with
   (530) NOT_ALLOWED - vhost soc not found while InfluxDB and Elasticsearch succeeded. The
   official rabbitmq image has no declarative vhost setting, so Compose cannot do it. The
   earlier "RabbitMQ is live-verified" claim was true only against a volume that already
   had the vhost; a rebuild loses the entire event bus. The two rabbitmqctl commands are now
   in CLAUDE.md's bring-up section.

3. THE LLM DESCRIBED A PORTSCAN AS A FLOOD.  Covered separately in
   reports/llm_faithfulness_report.txt and the commit that fixed it. The prompt, not the
   model, was wrong: render_few_shots substitutes the live alert's own predicted label into
   the example's input while the example's behaviour clause was hardcoded to a flood.

A DEMO TRAP, DOCUMENTED RATHER THAN FIXED
-----------------------------------------
write_influx_point uses the alert's own `timestamp` as the point time. For a flow replayed
from CICIDS-2017 that is 2017-07-05, so this alert reports influxdb=ok truthfully and the
point is genuinely stored -- at 2017-07-05 10:47:00, where the Grafana dashboard's recent
windows cannot see it. Verified: a -30d query returns nothing for it, a 2017 range returns
it with risk_score=100.

Set Grafana's time range to the capture window when demonstrating on replayed data. This is
deliberately not changed to wall-clock, which would assert that 2017 traffic happened today
-- a worse misrepresentation than an empty panel. MTTD is unaffected either way: it is the
ingested_at -> detected_at difference, which is preserved regardless of the absolute time.

ALSO CORRECTED
--------------
assemble_alert_context's docstring called score_latency_s the "MEASURED per-row scoring
latency". It is the run's mean: all rows score in one vectorised pass, so no per-row figure
exists, and every alert in a run reports the same mttd_ms. Correct for a batch, wrong to
read as a per-flow measurement. Only the docstring changed; computing it per row would mean
abandoning vectorised scoring to measure the thing less accurately.
