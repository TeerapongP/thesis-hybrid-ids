4. RETRIEVAL STRATEGY: CUSTOM HYBRID (BM25 + DENSE), NOT LANGCHAIN
======================================================================
Full reasoning recorded in models/rag_retrieval_config.json's "retrieval_strategy"
section. Summary: the knowledge base is small (45 chunks) and static, this repo has an
established precedent of small hand-written modules (fusion_layer.py, feature_extractor.py)
over framework dependencies, and this project's per-category evaluation culture wants
every retrieval-score component directly inspectable rather than delegated to a
retriever-chain abstraction. LangChain was not installed anywhere and is not used.

Hybrid combination: weighted linear combination of min-max-normalized scores, computed
over the FULL 45-chunk universe per query (not an ANN top-k subset, since the corpus is
tiny enough that exact scoring against all 45 is trivial):
  - dense component: ChromaDB collection.query() cosine similarity (1 - distance)
  - sparse component: rank_bm25.BM25Okapi over a lowercase + word-boundary tokenizer,
    rebuilt in-memory from the chunks fetched back out of the persisted ChromaDB
    collection at every RagRetriever() init (not persisted separately -- single
    on-disk source of truth, no risk of the BM25 corpus drifting from the vector store)
  - weights: dense=0.5 / bm25=0.5 (equal, per diagrams/thesis_dataflow_v2.drawio's
    "BM25 (Exact Match) + Dense Vector (Semantic)" listed with no stated priority; NOT
    tuned against the evaluation query set, which would be leakage)
  - top_k: 3, read from .env's RAG_TOP_K

6. PRECISION@3 EVALUATION
======================================================================
Query set: config/mitre_mapping.csv, dataset=='cicids2017', 14 rows (BENIGN EXCLUDED
EXPLICITLY -- it is the 15th CICIDS-2017 Label value but maps to no technique_id, so it
is not part of this evaluation, not silently dropped). Read-only: mitre_mapping.csv was
never used to influence chunking/embedding/indexing (see src/rag_retrieval.py's
no-leakage docstring) -- only this evaluation script reads it, after the index already
exists.

Query text used: the CICIDS-2017 attack category name itself (source_label, e.g. "DoS
Hulk", "PortScan", "SSH-Patator") -- deliberately NOT technique_name from the mapping
CSV, since technique_name is derived from the ground-truth technique_id and using it as
the query would leak the answer into the query itself, making the evaluation trivial.

Relevance rule: a retrieved chunk counts as relevant if its technique_id metadata
matches the expected technique_id, OR (for mitigation chunks) the expected technique_id
appears in its technique_ids list. Precision@3 = (# relevant chunks in top-3) / 3, per
category -- see reports/rag_retrieval_precision_at_3.csv for all 14 rows plus the
aggregate. NOT reported as a single blended number, per this repo's established
per-category convention (random_forest_val_metrics.csv, isolation_forest_loao_results.csv).

10/14 categories hit at least one relevant chunk in the top-3. The 4 misses share a
common, explainable pattern, not a code defect: each category's CICIDS-2017 Label
string is a tool/CVE/protocol name rather than a behavioral description, and the
underlying MITRE technique text (description/detection fields actually chunked) does
not literally contain that name:
  - "FTP-Patator" / "SSH-Patator": the tool name "Patator" appears nowhere in T1110.001's
    chunked text (which discusses password guessing behavior generically, not any named
    tool), so a bare query of the tool name alone does not lexically or (apparently)
    semantically pull T1110.001 into the top-3 ahead of other technique chunks.
  - "Bot": a highly generic English word; T1071.001's actual chunked text is about C2
    over web protocols (HTTP/S/WebSocket beaconing), which "Bot" alone does not strongly
    disambiguate from Discovery/Impact technique chunks.
  - "Heartbleed": T1190's chunked description/detection text never mentions "Heartbleed"
    or "CVE-2014-0160" -- that CVE annotation exists only in config/mitre_mapping.csv's
    technique_name column ("Exploit Public-Facing Application (CVE-2014-0160)"), which
    is deliberately excluded from the query to avoid leakage. A bare "Heartbleed" query
    against the actual indexed text has genuinely weak overlap with T1190's content.
This is reported as a real retrieval-quality finding (the query text convention chosen
-- using the natural attack-category label rather than any ground-truth-derived string
-- is what a real downstream consumer, e.g. Random Forest's predicted multi-class label,
would actually have at query time), not something to "fix" by changing the query
convention to leak more ground truth into it, and not a reason to alter the fixed
Phase 2 chunking plan.

6.1 POST-BASELINE INVESTIGATION AND FIX (2026-07-14)
======================================================================
Before accepting the 0.4524 baseline as final, the 4 misses were investigated
individually -- actual query text, actual top-3 retrieved chunks, and actual dense/BM25
score breakdown per chunk (not just the root-cause summary) -- to check for any
legitimate, non-leaking improvement. Full investigation:

FTP-Patator / SSH-Patator -- root cause was a retriever BUG, not a vocabulary gap.
  Per-component diagnostic (dense vs. bm25 score, not just combined) showed bm25=0.0 for
  EVERY one of the 45 chunks on both queries. Cause: src/rag_retrieval.tokenize's regex
  (r"[A-Za-z0-9_./-]+") kept '-' inside the token character class, so "FTP-Patator"
  tokenized as ONE token ('ftp-patator') instead of two ('ftp', 'patator'). That compound
  token exists nowhere in the 45-chunk corpus, so BM25 contributed exactly zero to the
  ranking for these 2 queries -- even though "SSH (22/TCP)" and "FTP (21/TCP)" appear
  verbatim, as separate tokens, in T1110.001's own chunked description. Checked all 14
  queries: FTP-Patator/SSH-Patator are the ONLY 2 containing a hyphen with no surrounding
  whitespace (the "Web Attack - X" categories have spaces around their hyphen and already
  tokenized correctly) -- so removing '-' from the token regex is a general, query-
  agnostic tokenizer fix, not a rule targeted at these 2 categories.
  FIX APPLIED: src/rag_retrieval.py's _TOKEN_RE changed to r"[A-Za-z0-9_./]+".
  RESULT: FTP-Patator 0.00->0.33 (miss->hit), SSH-Patator 0.00->0.33 (miss->hit).
  NOT LEAKAGE: the fix touches only how text (any text, query or corpus) is split into
  tokens -- it has no dependency on technique_id, technique_name, or any per-category
  identity. It is NOT the case that only these 2 categories' scores changed, though --
  2 more shifted as a side effect (see the NET PICTURE and BEFORE/AFTER table below for
  the full accounting; an earlier draft of this paragraph claimed "only these 2 changed,"
  which was wrong and has been corrected here).

Bot / Heartbleed -- investigated, found to be genuine gaps, left unfixed.
  Checked whether MITRE's own STIX data (both the local data/knowledge_base/
  mitre_techniques.json snapshot AND the live https://attack.mitre.org/techniques/T1190/
  and .../T1071/001/ pages, fetched directly) contains any legitimate signal that could
  close these gaps without leaking the answer:
    - Heartbleed / CVE-2014-0160: absent from T1190's description, detection, AND
      MITRE's live page (which cites other CVEs for T1190 -- e.g. CVE-2016-6662,
      CVE-2021-44228, CVE-2024-3400 -- but never CVE-2014-0160 or "Heartbleed"/"OpenSSL").
      There is no real MITRE source content to add here; fabricating a Heartbleed mention
      that MITRE itself doesn't publish for T1190 would not be "using more of the fetched
      source data," it would be inventing content -- rejected.
    - Bot: MITRE's live T1071.001 procedure-examples table lists ~300 malware/software
      names, a few of which happen to contain "bot" as a substring within a proper noun
      (e.g. "Lokibot", "Saint Bot") -- but this is coincidental string overlap, not the
      technique's actual subject matter (C2 over HTTP/S/WebSocket), and pulling in that
      whole list just to make "Bot" substring-match would be data-dredging, not a
      principled content addition -- rejected. Separately confirmed: the literal words
      "bot"/"botnet" DO appear in this KB already, but only inside T1498 (Network DoS)
      and T1595 (Active Scanning)'s chunks -- i.e. the wrong techniques for this category
      -- which if anything actively pulls retrieval toward the wrong answer (T1498::detection
      ranks #3 for the query "Bot" precisely because of its "botnets" mention), confirming
      this is a real vocabulary/semantic gap, not an extraction omission.
  Query-side context was also checked: the only query-time signal a real downstream
  consumer (e.g. Random Forest's predicted multi-class label) would actually have is the
  category name string itself -- there is no richer behavioral-description text anywhere
  in this pipeline's actual outputs to draw from without inventing one, which would
  amount to a hardcoded per-category lookup table in different clothing. No legitimate
  query-side improvement was found for these 2 categories either.
  CONCLUSION: Bot and Heartbleed remain documented, unresolved limitations of this
  retrieval layer -- not because no one looked, but because every avenue checked would
  require leaking the answer (technique_id/technique_name) or fabricating source content
  MITRE does not actually publish.

NET PICTURE -- state plainly, for the thesis writeup, not just the aggregate number:
This was a genuine bug fix (BM25's token character class incorrectly glued hyphen-joined
compound queries into one out-of-vocabulary token), applied uniformly to all text, not a
change targeted at any specific category. Its net effect across the 14-category
evaluation was:
  - 2 categories FIXED (miss -> hit): FTP-Patator, SSH-Patator.
  - 2 categories INCIDENTALLY SHIFTED, both already hits before and after: Web Attack -
    Brute Force improved (0.67 -> 1.00) and Web Attack - XSS REGRESSED (0.67 -> 0.33).
    The XSS regression is real, evidence-based, and reported as such, not a false alarm
    to be explained away: the old (buggy) regex emitted a spurious standalone "-" token
    for any hyphen with surrounding spaces, and that stray token's BM25 contribution
    happened to help rank T1190::detection into XSS's old top-3; removing it (correctly,
    as part of fixing the real bug) cost that placement. In other words, the old buggy
    tokenizer was accidentally propping up one category's score using a token that
    shouldn't have existed in the first place, and fixing the bug removed that prop along
    with the bug.
  - 10 other categories unaffected (8 fully byte-for-byte identical; DDoS/DoS-family/
    PortScan/Web Attack - Sql Injection/Infiltration all unchanged -- see the table below).
  - 2 categories (Bot, Heartbleed) remain unresolved -- investigated and confirmed to be
    genuine vocabulary/semantic gaps, not touched by this fix (see above).
  NET: mean precision@3 0.4524 -> 0.5000, mean hit@3 0.7143 (10/14) -> 0.8571 (12/14) --
  a real aggregate improvement, but not a uniform one across every category.
  METHODOLOGY POINT (worth a sentence in the thesis discussion): fixing a genuine
  tokenizer bug does not guarantee every category's score moves in the same direction.
  A component that is broken can still, by coincidence, be propping up an unrelated
  metric elsewhere; correcting it can expose that dependency as a small regression
  alongside the intended, larger gain. The right response is to report the regression
  plainly (as done here) rather than treat "net improvement" as license to only report
  the categories that moved favorably -- the aggregate metric improving is not the same
  claim as "every category improved," and a thesis evaluation section should not
  conflate the two.
Full reasoning and rejected alternatives also recorded in
models/rag_retrieval_config.json's "bm25_tokenizer_fix_2026_07_14" key.
code-reviewer was invoked against this change; see Section 7 for the outcome and the
two corrections it required (this line originally, incorrectly, asserted the review had
already happened at the time this section was first drafted -- it hadn't; fixed here
after the review actually completed, not left as-is).
