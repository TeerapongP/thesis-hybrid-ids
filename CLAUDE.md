## Project overview

This repo is the working directory for a master's thesis on a **Hybrid Intrusion Detection System (IDS)** for a campus SOC. The intended pipeline (see `diagrams/thesis_ml_llm_pipeline_v3.drawio` and `diagrams/thesis_dataflow_fixed.drawio`) is:

1. **Data layer** — real PA-5220 firewall TRAFFIC/THREAT logs (primary, weakly labeled) + CICIDS-2017 and UNSW-NB15 (public benchmarks, used only for generalizability testing, not training) + a Python-injected synthetic attack overlay (≤5% of traffic: brute force, port scan, data exfil, C2 beacon, credential stuffing).
2. **Service/enrichment layer** — original design called for `enrich.py` (Kafka consumer that queries OpenCTI via GraphQL/pycti for IoC match + graph walk, still not implemented), `label_builder.py` (originally specified as weak supervision from OpenCTI confidence score: ≥0.70 → attack, <0.40 → normal), and `feature_extractor.py` (originally specified as 9 features: 5 network + 4 CTI). **What's actually implemented differs from this original spec** (superseded by direct instruction during implementation, see Commands below): `label_builder.py` does a static MITRE ATT&CK lookup-table join (`config/mitre_mapping.csv`), not OpenCTI weak supervision — that OpenCTI-based labeling is still `enrich.py`'s unbuilt future job; `feature_extractor.py` uses *every* numeric flow column as network features (78 for CICIDS-2017, 76 for UNSW-NB15 post CIC-UNSW-NB15 migration) rather than a hand-picked 5, plus the same 4 CTI features, `MinMaxScaler` fit on train only, and a capped (not full-`'auto'`) SMOTE. `build_cross_dataset_eval.py` then derives a column-aligned subset of both datasets' feature matrices for M1c cross-dataset generalizability testing (see Commands below). The hybrid BM25 + dense-vector RAG layer over ChromaDB is now implemented (`src/rag/rag_retrieval.py`, see "RAG Layer — knowledge base source decision" below for what it's built on and why it isn't fed from OpenCTI despite the diagrams showing that).
3. **ML ensemble layer** — Isolation Forest (unsupervised, scikit-learn) + Autoencoder (unsupervised, PyTorch) + Random Forest (supervised, scikit-learn), combined in a weighted/majority-vote ensemble fusion layer producing a 0–100 risk score with SHAP-based explainability.
4. **LLM explanation layer** — `src/llm/llm_explain.py` implements prompt construction, Ollama/llama.cpp HTTP calls, constrained JSON parsing, and the reconciled eight-field Thai output schema. `src/evaluation/eval_llm_layer.py` provides six offline contract checks and `models/llm_layer_config.json` records the decisions. The intended model remains **Typhoon2.1 12B Instruct**; live throughput/GPU verification is still pending because Ollama is not installed on this machine.
5. **Dashboard & notification layer** — **now implemented** (`src/notifications/alert_dispatcher.py`, `notify_line.py`, `notify_gmail.py`; see `HANDOFF_OUTPUT_LAYER.md`, built end-to-end per that handoff): `dispatch_alert(...)` routes by priority (HIGH → immediate, MEDIUM → queued, LOW → daily digest) over a RabbitMQ event bus (`soc` vhost, reusing the live `opencti-rabbitmq` broker), writes metrics to InfluxDB (visualized by the already-provisioned Grafana `SOC Overview` dashboard) and to Elasticsearch (`soc-alerts-*`, drilled into via Kibana's `SOC Alert Investigation` saved-object dashboard), and fans out to LINE (HIGH) and Gmail API (MEDIUM immediate / LOW daily digest — switched from the diagrams' original Outlook/Microsoft Graph API choice; see `HANDOFF_OUTPUT_LAYER.md`'s "notification channel decision superseded" note for why). RabbitMQ/InfluxDB/Elasticsearch paths are live-verified end-to-end; the LINE/Gmail sends are dry-run-only (LINE has a real token but this sandbox lacks outbound internet; Gmail's OAuth2 credentials are deliberately left blank — see "Notifications & Output Layer" below).

Evaluation design includes a 4-way ablation (rule-based SIEM / ML-only / LLM-only / proposed hybrid) and an A/B analyst triage-time study (≥15 analysts × 20 alerts/group, blinded).

**Current implementation state:** the full data-prep chain exists as code and has been run end-to-end: `eda_sanity_check.py` → `preprocess_pipeline.py` → `label_builder.py` → `feature_extractor.py` → `build_cross_dataset_eval.py` (all in `src/`, see Commands below). ## Commands

`pyproject.toml`/`uv.lock` are authoritative for service/runtime dependencies (RabbitMQ, Elasticsearch, InfluxDB, Gmail, LINE HTTP, ChromaDB, BM25) and the offline unit tests run with `uv run`. Heavy ML/notebook dependencies (`pandas`, `scikit-learn`, CUDA-enabled `torch`, `sentence-transformers`, etc.) remain on the system Anaconda interpreter because this machine's `torch==2.12.1+cu130` is matched to its RTX 3070; do not replace it with an unpinned CPU/CUDA wheel. Use `python` for the training/evaluation notebooks and `uv run python -m ...` for service-layer modules/tests.

All commands below are run from the **repo root** (not from inside `src/`):

Run the EDA sanity check (loads both datasets from `data/raw/`, checks structure/quality/class distribution/constant columns/timestamps, prints a report, and writes `reports/eda_report.txt`):
```bash
python -m src.evaluation.eda_sanity_check
```

Run the preprocessing pipeline (two independent sub-pipelines in one script — CICIDS-2017 runs first, then the `unswnb15` slot; neither touches the other's dataframe). Reads raw CSVs from `data/raw/`, writes outputs to `data/processed/`:
- **CICIDS-2017**: fixes the mojibake `Label` values, converts the `Init_Win_bytes_forward/backward` `-1` sentinel to `NaN`, then a general `clean_common()` step converts Inf to `NaN` and drops duplicate/NaN rows *excluding* those two sentinel columns so their NaNs survive for `feature_extractor.py` to impute/flag later — never add them back into a general dropna, or you'll silently drop ~1.4M rows. Also reports attack-category counts against a LOAO holdout threshold. Saves the full cleaned data to `data/processed/cicids2017_clean.parquet`, then a stratified-by-`Label` 60/20/20 train/val/test split (`random_state=42`) to `data/processed/cicids2017_{train,val,test}.parquet` for the main M1a train/val/test metric cycle — this split is separate from the LOAO holdout experiments below, which reuse the full cleaned dataset differently.
- **`unswnb15` (now sources from CIC-UNSW-NB15, not the old raw UNSW-NB15 4-file format — migrated 2026-07-02)**: `load_unsw()` reads `data/raw/cic-unsw-nb15/Data.csv` + `Label.csv` and joins them positionally (see `data/raw/` entry above for why that join is trusted), renames Data.csv's 19 divergently-named CICFlowMeter columns to match CICIDS-2017's naming via `CIC_UNSW_COLUMN_RENAME` (e.g. `Total Fwd Packet`→`Total Fwd Packets`, `FWD Init Win Bytes`→`Init_Win_bytes_forward`), then derives `attack_cat` (string, `NaN`=Benign) and a binary `Label` from `Label.csv`'s 0–9 codes via `CIC_UNSW_LABEL_CODE_MAP` (from `Readme.txt`) — both columns come from the same source code so they're consistent by construction; `clean_unsw()` now just logs + asserts that. This replaces the old `clean_unsw()`'s whitespace-strip/`Backdoors`→`Backdoor` fix and `sport`/`dsport`/`ct_ftp_cmd` mixed-type-column cast, both **removed** because they no longer apply (`attack_cat` is derived clean already; `Data.csv` has none of those columns — confirmed all 76 columns are numeric, 0 NaN/Inf, no `-1` sentinel in the renamed Init-Win-Bytes columns) — if you ever need the old raw-UNSW-NB15 code path back, it's only in git-less local history/this file's memory, not recoverable from the current code. `clean_common()` is called with `sentinel_cols=[]` (no sentinel columns exist for this source). Saves to `data/processed/unswnb15_clean.parquet` (306,173 rows post-dedup, down from 447,915 — `clean_common()` drops 141,742 duplicate rows, ~31.6%) and the same stratified 60/20/20 split to `data/processed/unswnb15_{train,val,test}.parquet`. `label_builder.py` required **no code changes** for this swap — its `attack_cat`-based join already worked against the new source's category-name strings unmodified, confirmed by a 0-unmapped rerun.
- **LOAO (Leave-One-Attack-Out) zero-day holdout, CICIDS-2017 only**: `build_loao_split(df, holdout_category)` builds one train/zero-day-test pair per qualifying attack category, for testing whether the unsupervised components (Isolation Forest, Autoencoder) can still catch an attack type they never saw in training. Runs on the cleaned full `df` (equivalent to `cicids2017_clean.parquet`), independent of `split_train_val_test()` — train = all BENIGN except a held-out 20% + every attack category except `holdout_category`; zero-day test = that held-out BENIGN slice + only `holdout_category`'s rows (`random_state=42`). Loops automatically over whichever categories clear the `n≥1000` LOAO threshold (`LOAO_MIN_SAMPLES`, currently 10: DoS Hulk, DDoS, PortScan, DoS GoldenEye, FTP-Patator, DoS slowloris, DoS Slowhttptest, SSH-Patator, Bot, Web Attack - Brute Force) — the 4 categories below that threshold (Web Attack - XSS, Infiltration, Web Attack - Sql Injection, Heartbleed) stay qualitative-only per `report_attack_categories()` and get no LOAO pair. Output per category: `data/processed/loao/loao_{category}_train.parquet` and `data/processed/loao/loao_{category}_zeroday_test.parquet` (category slugified: lowercased, whitespace/hyphens collapsed to `_`, e.g. `Web Attack - Brute Force` → `web_attack_brute_force`). **Important for downstream analysis**: the BENIGN/attack ratio in each zero-day test set is *not* controlled — it's whatever that category's natural prevalence is (ranges from 29.20% attack for DoS Hulk down to 0.35% for Web Attack - Brute Force), so Recall/FPR are not comparable at face value across categories and must be reported per-category rather than averaged as if equally weighted.

### Notebooks (ML ensemble layer)

`notebooks/01_isolation_forest.ipynb` builds and evaluates **only** the Isolation Forest ensemble member, on CICIDS-2017 (`data/features/cicids2017_features_{train,val,test}.parquet`); UNSW-NB15 and the Autoencoder/Random Forest members are left for later. Run it from within `notebooks/` (it resolves `ROOT` to the repo's parent directory) using the system/Anaconda Python kernel, not the `.venv` (see note above). Conventions established here that later ensemble notebooks should match:
- **Label/score remapping**: sklearn's `IsolationForest.predict` returns `-1`=anomaly/`1`=normal and `score_samples` is higher-is-more-normal — both are flipped once, explicitly, to the project-wide convention `1`=anomaly/`0`=normal and higher `anomaly_score`=more anomalous, since mismatched conventions across ensemble members would silently corrupt the later Fusion Layer.
- **CTI-encoded columns excluded from model input**: `technique_id_encoded`, `tactic_encoded`, `mapping_confidence_encoded`, `is_known_technique` are deterministic functions of the true `Label`/`attack_cat` (via `label_builder.py`'s static MITRE lookup), not real-world available at detection time — a first run of this notebook included them (84 features) and inflated every metric (e.g. AUC-ROC 0.8549 vs. the corrected 0.7286); they're reserved for the downstream LLM explanation layer, not any of the three detection models. `NON_FEATURE_COLS`/`select_feature_columns` in the notebook encode this exclusion — reuse the same list when building the Autoencoder/Random Forest notebooks.
- **Contamination tuning**: `contamination='auto'` hardcodes sklearn's decision threshold (`offset_ = -0.5`), unrelated to the data's actual anomaly rate — the notebook sweeps explicit values (`[0.05, 0.10, 0.15, 0.20]`) against validation F1 and found `0.2` best (F1 0.542 vs. 0.368 for `'auto'`); AUC-ROC is identical across all sweep values (confirmed via an in-notebook assertion) since contamination only moves the cutoff, not the tree-based ranking. The final saved model (`models/isolation_forest.pkl`) is refit with `contamination=0.2`.
- **Detection is heavily category-dependent**, not uniform: at the tuned threshold, per-category recall on the CICIDS-2017 val set ranges from 0.0 (FTP-Patator, SSH-Patator, Web Attack - Sql Injection, Web Attack - XSS) up to 1.0 (Heartbleed, n=2). Volumetric/flooding attacks (DoS Hulk, DDoS, DoS GoldenEye/Slowhttptest/slowloris) are caught reasonably well; low-and-slow / low-volume attacks (patator brute-forcers, PortScan, Bot, small web attacks) are essentially invisible to this unsupervised model regardless of threshold — expected to be exactly the gap the supervised Random Forest member and/or LLM layer need to cover.
- **LOAO (zero-day) evaluation** in §6 reuses `data/processed/loao/loao_{category}_{train,zeroday_test}.parquet` — these predate `feature_extractor.py` (78 raw unscaled CICFlowMeter columns only, no CTI columns, `Init_Win_bytes_forward/backward` still `-1`→`NaN`-sentineled), so each fold does its own train-only median imputation before fitting; tree-based Isolation Forest is scale-invariant, so training unscaled here isn't a methodological inconsistency with the scaled main-model run. Results per category are broadly consistent with the in-dataset per-category recall pattern above (e.g. DoS Hulk 0.90 recall vs. PortScan/FTP-Patator/SSH-Patator near 0).
- Outputs: `models/isolation_forest.pkl` (final tuned model), `reports/isolation_forest_val_metrics.csv`, `reports/isolation_forest_contamination_sweep.csv`, `reports/isolation_forest_loao_results.csv`, `data/features/cicids2017_isoforest_scores_val.parquet` (val-set anomaly scores, `row_index`-joinable against later ensemble members' scores on the same split). **Option A (behavioral/time-windowed features) is adopted, with this exact scope — do not oversimplify this in future sessions.** A separate branch (`behavioral-time-windowed-features`) added per-source-IP time-windowed behavioral features (`conn_count`/`uniq_dport_count`/`fail_ratio`/`repeat_ratio` × 1/3/5-minute windows, 12 columns total) computed from the `GeneratedLabelledFlows/TrafficLabelling` raw distribution (see `src/features/behavioral_feature_extractor.py`), since the standard `MachineLearningCSV`-derived pipeline has no `Source IP`/`Timestamp` to compute them from. After a multi-phase validation (row-hash-join audit finding and fixing a dtype-mismatch false negative, then a properly pipeline-integrated retrain — see "Notebooks (behavioral feature engineering, Option A)" below for the full trail), the decision is: **the 92-feature behavioral set (78 raw CICFlowMeter + 2 sentinel-missing-flag + 12 behavioral) is now the standard input for Isolation Forest and Autoencoder going forward.** Random Forest is explicitly **out of scope for this migration and stays on the original 80-feature capped-SMOTE set** (`data/features/cicids2017_features_*.parquet`) — behavioral features didn't change its known LOAO weakness (near-zero zero-day recall on Bot/PortScan/SSH-Patator), because that weakness is a supervised-generalization limitation (a model can't recognize a category it never saw one example of), not a feature-representation one that richer features could fix.

The per-category nuance behind this decision, confirmed across three separate evaluations (an initial standalone/unvalidated prototype, then the properly Phase 1+2 pipeline-integrated retrain, then a LOAO re-run on that same integrated population) — report these per-category, not as a single blended "behavioral features help" claim:
- **DDoS**: a fully confirmed, robust zero-day recall gain for both Isolation Forest and Autoencoder, essentially unaffected by which population (unvalidated prototype vs. properly join-validated) trained the model.
- **PortScan, Autoencoder**: also a fully confirmed, robust zero-day gain (recall ~0.78 vs. a ~0.01 baseline), holding up almost exactly across both populations.
- **PortScan, Isolation Forest**: a *real* zero-day gain over the 80-feature baseline (0.002 → ~0.15 recall), but **substantially smaller than the unvalidated prototype's number suggested** (0.46) — more than halved once evaluated on the properly row-hash-join-validated population. Isolation Forest's PortScan zero-day detection is notably more sensitive to the exact BENIGN population used than Autoencoder's is; don't cite the prototype's 0.46 figure as current.
- **Bot, FTP-/SSH-Patator, Web Attack - Brute Force**: unchanged and still essentially undetectable zero-day (recall near 0) regardless of feature set, model, or which population was used. The original motivating hypothesis — that time-windowed behavioral features would specifically help catch low-and-slow brute-force-style attacks — is **not supported** by any of the three evaluations. This remains an open problem, not one Option A solves.

A necessary side effect of adopting the behavioral set: the row-hash join between the two independently-produced CICFlowMeter distributions could only match ~76.4% of BENIGN rows (100% of every attack category matched) — the unmatched ~23.6% of BENIGN is dropped and documented, not imputed or guessed. This shrinks Autoencoder's real BENIGN training population (960,726 vs. the original pipeline's 1,257,033) and is the leading explanation for the modest in-dataset F1 regression found in the properly-integrated retrain (0.889 vs. an unvalidated prototype's 0.914) — a cost that, per the per-category LOAO results above, mostly did *not* carry through to a zero-day-recall cost. Each retrained model's population size is also no longer row-for-row identical to Random Forest's — `orig_row_index` (added to the behavioral pipeline's output, threaded through Phase 1 and Phase 2) is the join key the Fusion Layer uses to align these models' scores against Random Forest's, instead of assuming positional `row_index` equality, which would silently misalign once row counts diverge. **The Fusion Layer migration itself (`models/isolation_forest_behavioral_v2.pkl`, `models/autoencoder_behavioral_v2.pt`, and the existing `models/random_forest.pkl`, joined via `orig_row_index`) is now done** — see `notebooks/08_fusion_layer.ipynb` and "Notebooks (Fusion Layer, Option A integration)" below.

### RAG Layer — knowledge base source decision (OpenCTI investigated, permanently not adopted)

`data/knowledge_base/mitre_techniques.json` (the Phase 1 knowledge base behind the RAG layer's approved 45-chunk design — 11 techniques, `T1046, T1059, T1071.001, T1110, T1110.001, T1190, T1210, T1498, T1499.002, T1505.003, T1595`) is sourced from a direct fetch of the raw `mitre-attack/attack-stix-data` GitHub STIX bundle (`enterprise-attack/enterprise-attack.json`, ATT&CK v19.1), **not** from OpenCTI, even though the architecture diagrams (`diagrams/thesis_dataflow_v2.drawio` etc.) show OpenCTI → Vector DB. This was a deliberate choice, investigated thoroughly (2026-07-17) and closed permanently — do not re-open this question in a future session without new evidence (e.g. a confirmed OpenCTI upstream release that adds Detection Strategies support or fixes the dedup bug below).

**Why the GitHub-STIX source was kept instead of switching to OpenCTI's GraphQL API**, despite OpenCTI running locally (`opencti-connector-mitre-1`, healthy, already ingesting this same MITRE ATT&CK data) and being the architecturally "correct" source per the diagrams — live investigation against the running instance (platform + connector both pinned at `opencti/*:5.12.17` in `opencti/docker-compose.yml`) found two content gaps, both confirmed structural rather than simple version lag:

1. **Detection guidance is 100% absent, not just outdated.** `AttackPattern.x_mitre_detection` came back empty for all 11/11 target techniques — confirmed via the raw `toStix` STIX2 JSON (the key doesn't exist on the object at all), and a full introspection of the platform's 757 GraphQL types found zero types related to `DetectionStrategy`/`Analytic` (the newer ATT&CK data model that the original Phase 1 extraction had to reconstruct rich "Analytic NNNN: ..." detection text from, since it's no longer a flat STIX field). This isn't fixable by upgrading: the current **master** (unreleased) branch of `opencti/connector-mitre` still requires only `OpenCTI Platform >= 6.x` and its own entity-mapping table still has no `x-mitre-detection-strategy`/`x-mitre-analytic` row; Filigran's own OpenCTI v7.0 feature announcement (latest release checked, `7.260715.0`) makes no mention of Detection Strategies/Analytics anywhere; and **[opencti#11521](https://github.com/OpenCTI-Platform/opencti/issues/11521)** ("x-mitre-asset Not Supported – MITRE Connector Fails on ATT&CK v17.1 Import," opened June 2025, still open/unresolved) is direct, general evidence that OpenCTI's custom-STIX-type support lags MITRE's ATT&CK schema evolution as a pattern, not a one-off gap. Nobody has built this upstream yet, at any released version — this is a missing feature, not a config or version problem.
2. **Mitigation content gets corrupted by a platform-level entity-merge bug, not a connector quirk.** Querying `coursesOfAction` on Enterprise techniques returned ICS-domain mitigation IDs/text instead of the expected Enterprise ones (e.g. T1046 expected `M1030`/`M1031`/`M1042`; OpenCTI returned `M0930`/`M0931`/`M0942` with much shorter, generic ICS-style descriptions in place of the detailed Enterprise text). Pulling the merged entity's own external references confirmed the root cause: a single OpenCTI record carries **both** `attack.mitre.org/mitigations/M1030` and `attack.mitre.org/mitigations/M0930` as external refs, having kept only the ICS `x_mitre_id`/description. OpenCTI's own deduplication docs (checked against **current/latest** docs, describing 7.x behavior) still state Course-of-Action entities are matched by `("name" OR "alias") AND optional "x_mitre_id"` — an `OR name` rule that structurally allows same-named mitigations from different ATT&CK domains to merge. This is platform-level entity-resolution logic (applies "whether manually by a user or automatically by the connectors/workers chain" per OpenCTI's docs), not something a connector version bump touches. **[opencti#1026](https://github.com/OpenCTI-Platform/opencti/issues/1026)** ("Change the Attack Pattern / Courses Of Action standard IDs," closed/"Solved" in release **4.1.0, 2021**) shows OpenCTI attempted to fix exactly this class of ID-generation problem five years ago — yet the collision reproduces live on the current 5.12.17 instance, and the current docs describe the same name-matching rule as intended present-day behavior. No evidence of a fix for the cross-domain case was found in any changelog/issue search.

Given both gaps are architectural (missing feature; documented-as-intended dedup rule) rather than version lag, and the only upgrade path that touches either one is a full platform upgrade (`5.12.17` → current `7.260715.0`/LTS `7.260309.0-lts.6`, crossing OpenCTI's own versioning-scheme change from semver to calendar-versioning, i.e. at least two major-version generations) against a live instance with real ingested data across 9 running connectors — the risk/reward was judged not worth it for either issue, and neither has a safe isolated (connector-only) test path since both require the platform bump just to reach the code path that might matter. **Decision: keep the static GitHub-STIX snapshot as `mitre_techniques.json`'s source, permanently.** OpenCTI's role in this thesis stays as Output Layer infrastructure (Elasticsearch/RabbitMQ backend, see `observability/`) and a production-readiness demonstration — not the RAG knowledge base source. See `HANDOFF_RAG_PHASE3.md`'s addendum for the same record in the phase-brief file.

### Bringing up the infrastructure stacks

The shared Docker network must exist before any stack starts (only `network/docker-compose.network.yml` creates it as a named/non-external network the first time; other composes reference it as `external: true`):
```bash
docker network create soc_shared
docker compose -f network/docker-compose.network.yml up -d
docker compose --env-file opencti/.env -f opencti/docker-compose.yml up -d
docker compose --env-file observability/.env -f observability/docker-compose.yml up -d
docker compose --env-file notification/.env -f grafana/docker-compose.yml up -d
```
Each stack's `.env` file holds real credentials/tokens; never print or commit their contents. The Compose commands above name each stack's env file explicitly.

`observability/.env.example` lists the three required InfluxDB initialization keys. Add them with unique values to the ignored `observability/.env`; Compose exits if any are missing. `opencti/.env.example` lists the platform bootstrap token, the worker token, and one token variable per connector. OpenCTI 5.12.17 documents the worker token as requiring an administrator account with bypass capability, so provision a dedicated worker service identity with that required privilege and set `OPENCTI_WORKER_ADMIN_TOKEN`; do not reuse the platform bootstrap token. Create a separate least-privilege Connector-role account/token for each connector and set its matching `OPENCTI_*_CONNECTOR_TOKEN` variable. Only the platform receives `OPENCTI_ADMIN_TOKEN`. Compose fails closed until these credentials are provisioned in the ignored `opencti/.env`.

**Grafana admin credentials — resolved 2026-07-18, deliberate volume reset, user-authorized.** A prior session found the live Grafana instance's admin password wasn't the documented `admin`/`admin` default and wasn't recorded anywhere in this repo (see git history around 2026-07-18 for the original incident writeup if needed) — root-caused to the `grafana_grafana-data` volume (created 2026-05-04, predating the Dashboard & Notification Layer work) already holding a different, unrecovered password by the time anyone needed real API/UI access. **Before resetting anything, the volume's `grafana.db` was inspected read-only** (copied out via `docker cp` from the running container, queried directly with `sqlite3`/Python — no live credential needed for this, since it bypasses Grafana's own auth entirely): it held exactly 1 user (`admin`, no others), and every dashboard/folder/datasource present (`SOC Overview` dashboard + its `Thesis SOC` folder, `InfluxDB-SOC`/`Elasticsearch-SOC` datasources) was already file-provisioned from `grafana/dashboards/soc-overview.json` and `grafana/provisioning/{dashboards,datasources}/*.yml` — confirmed via the `dashboard_provisioning` table's recorded checksum against the actual on-disk file. Zero alert rules, annotations, API keys, snapshots, teams, or playlists existed. **Nothing of value would be lost by wiping the volume** — everything meaningful was already reproducible from files already in this repo.

Grafana now receives only the explicitly listed admin and datasource settings from `notification/.env`; the broad `env_file` injection is removed. Compose requires `GF_SECURITY_ADMIN_USER` and `GF_SECURITY_ADMIN_PASSWORD` plus the datasource settings, and has no vendor credential fallback. The current local Grafana password matches the vendor default and must be rotated to a unique password in the ignored `notification/.env` before startup; its value is not recorded here. Use `notification/grafana.env.example` as the key template. Compose interpolation does not rotate an already initialized Grafana database, so an existing volume may need an authenticated password change or a separately authorized reset.

Historical runtime verification on 2026-07-18 used the then-current local credentials and volume. It does not verify the current compose configuration or any later credential rotation; the Grafana host port is now limited to loopback.

## Working with the datasets

**Note on `eda_sanity_check.py` vs. `preprocess_pipeline.py` currently disagreeing about the UNSW source**: `eda_sanity_check.py` was not touched during the CIC-UNSW-NB15 migration and still loads/reports on the *old* raw UNSW-NB15 4-file format (`UNSW-NB15_1..4.csv`, still present in `data/raw/` but no longer used by `preprocess_pipeline.py`). Its UNSW-related findings below no longer describe what actually feeds the `unswnb15` pipeline slot — treat them as historical/archived, relevant only if `eda_sanity_check.py` is updated or the old format is ever revived.

Known quirks (already handled in `eda_sanity_check.py`, keep these in mind for any new preprocessing script):
- CICIDS-2017 column names have stray leading/trailing whitespace — must `.str.strip()` them.
- CICIDS-2017's public `MachineLearningCVE` distribution has no `Timestamp`/IP/port columns (stripped for privacy); only `GeneratedLabelledFlows` has real timestamps, needed later for simulated replay feeds.
- *(old raw UNSW-NB15 format, archived — see note above)* `NUSW-NB15_features.csv` (feature name reference) is `cp1252`-encoded, not UTF-8; the raw `UNSW-NB15_*.csv` data files have no header row, so column names must be assigned from that features file. `UNSW-NB15_1.csv` has a BOM; reading everything as `utf-8-sig` is safe.
- *(old raw UNSW-NB15 format, archived)* `attack_cat` and `Label` (binary) were two independently-sourced columns that had to be cross-checked for consistency (non-null/non-empty `attack_cat` should imply `Label == 1`). CIC-UNSW-NB15 doesn't have this problem — `preprocess_pipeline.py`'s `load_unsw()` derives both `attack_cat` and `Label` from the same `Label.csv` numeric code, so they're consistent by construction (`clean_unsw()` now just asserts this rather than reconciling two independent sources).
- Both datasets contain duplicate rows and out-of-range values (inf/-inf in CICIDS `Flow Bytes/s`-style rate columns); nothing is dropped/imputed/scaled in the sanity-check stage — that belongs in a separate future preprocessing script.
- CICIDS-2017 `Label` values like `Web Attack – Brute Force` are mojibake at the source (the dash was already corrupted to U+FFFD before distribution, confirmed via raw byte inspection — not a wrong-encoding-choice bug on our end). Read with `utf-8-sig` as usual; re-reading as `cp1252` makes it worse. `preprocess_pipeline.py` normalizes `–`/`—`/`�` to a plain `-` so labels are at least consistent enough to map to MITRE, but the original dash is not recoverable.
- CICIDS-2017's `Init_Win_bytes_forward`/`Init_Win_bytes_backward` use `-1` as a CICFlowMeter sentinel meaning "not measured," not bad data — convert to `NaN` for only these two columns rather than treating them with general negative-value cleaning, and never drop those rows (it would discard >1/3 of the data). CIC-UNSW-NB15's equivalent renamed columns have no such sentinel (confirmed empirically: min value 0, zero `-1`s), so no analogous handling was needed there.
- CIC-UNSW-NB15's `Data.csv` has substantial duplicate rows (141,742 of 447,915, ~31.6%) removed by the same `clean_common()` dedup step used for the other two datasets — unlike the CICIDS/old-UNSW sentinel columns, there's no NaN-preservation subtlety here, it's a plain full-row dedup.
