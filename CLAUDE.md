## Project overview

This repo is the working directory for a master's thesis on a **Hybrid Intrusion Detection System (IDS)** for a campus SOC. The intended pipeline (the architecture diagrams now live outside this repo, in `E:\thesis-doc\03_Diagrams\`, e.g. `thesis_dataflow_v4.drawio` / `thesis_dataflow_v5.html`) is:

1. **Data layer** — **CICIDS-2017 is the primary and only training dataset.** The PA-5220 firewall logs the diagrams call primary were never obtained and are **permanently out of scope** (user decision, 2026-10-25): do not design against them, and do not list them as a data source. CIC-UNSW-NB15 is the second dataset, used only for M1c cross-dataset generalizability, never for training. The Python-injected synthetic attack overlay (≤5% of traffic: brute force, port scan, data exfil, C2 beacon, credential stuffing) is **now implemented** — `src/ingestion/synthetic_overlay.py`, see "Synthetic attack overlay and MTTD" below.
2. **Service/enrichment layer** — **`enrich.py` is now implemented** (`src/services/enrich.py`, see "OpenCTI enrichment service" below) — the Kafka consumer that queries OpenCTI for IoC match + graph walk and publishes `pa5220.enriched`. The original design also called for `label_builder.py` (originally specified as weak supervision from OpenCTI confidence score: ≥0.70 → attack, <0.40 → normal), and `feature_extractor.py` (originally specified as 9 features: 5 network + 4 CTI). **What's actually implemented differs from this original spec** (superseded by direct instruction during implementation, see Commands below): `label_builder.py` does a static MITRE ATT&CK lookup-table join (`config/mitre_mapping.csv`), not OpenCTI weak supervision; `enrich.py` enriches events with indicators and graph-walk context, it does not do weak-supervision labelling, so that part of the original spec stays unbuilt by design; `feature_extractor.py` uses *every* numeric flow column as network features (78 for CICIDS-2017, 76 for UNSW-NB15 post CIC-UNSW-NB15 migration) rather than a hand-picked 5, plus the same 4 CTI features, `MinMaxScaler` fit on train only, and a capped (not full-`'auto'`) SMOTE. `build_cross_dataset_eval.py` then derives a column-aligned subset of both datasets' feature matrices for M1c cross-dataset generalizability testing (see Commands below). The hybrid BM25 + dense-vector RAG layer over ChromaDB is now implemented (`src/rag/rag_retrieval.py`, see "RAG Layer — knowledge base source decision" below for what it's built on and why it isn't fed from OpenCTI despite the diagrams showing that).
3. **ML ensemble layer** — Isolation Forest (unsupervised, scikit-learn) + Autoencoder (unsupervised, PyTorch) + Random Forest (supervised, scikit-learn). **The deployed fusion rule is `confidence_weighted`: trust Random Forest where `|P(attack) - 0.5| * 2 >= 0.95`, otherwise fall back to `(if_norm + ae_norm) / 2`, and alert above 0.03.** All three members contribute, so the "three-model ensemble" framing does hold — but Isolation Forest only decides rows RF left undecided, because its LOAO FPR of 0.09–0.15 makes it unusable as an independent trigger. This replaced the `rf_ae_or` OR rule on 2026-11-01; see "Fusion Layer" below for the ablation that forced the change. The 0–100 risk score comes from `alert_dispatcher.py` clamping and scaling the fused score. **SHAP explainability is implemented and migrated to this rule** (`src/modeling/shap_explain.py`): it attributes whichever branch decided a row, and for fallback rows it attributes the composite `(if_norm + ae_norm) / 2` directly — possible for the first time because all three members now share one feature space. See "SHAP explainability" below.
4. **LLM explanation layer** — `src/llm/llm_explain.py` implements prompt construction, Ollama/llama.cpp HTTP calls, constrained JSON parsing, and the reconciled eight-field Thai output schema. `src/evaluation/eval_llm_layer.py` provides six offline contract checks and `models/llm_layer_config.json` records the decisions. The intended model is **Typhoon2 8B Instruct** (Llama 3.1 base, Ollama tag `scb10x/llama3.1-typhoon2-8b-instruct`; switched from Typhoon2.1 12B Instruct on 2026-10-25); it runs fully on the RTX 3070 GPU at about 67 tokens/s (verified 2026-10-25, see `models/llm_layer_config.json`), and the few-shot copying and remediation loop are fixed (remediation capped at 5 unique items, repeat_penalty 1.15). `priority` is now set by the deterministic `derive_priority` rule (provisional HIGH cutoff fused_score >= 0.80), not by the LLM; the LLM writes only `explanation_th` and `remediation`. Output quality is still not verified on more than two live alerts (see `quality_issues`).
5. **Dashboard & notification layer** — **now implemented** (`src/notifications/alert_dispatcher.py`, `notify_line.py`, `notify_gmail.py`; see `docs/handoffs/HANDOFF_OUTPUT_LAYER.md`, built end-to-end per that handoff): `dispatch_alert(...)` routes by priority (HIGH → immediate, MEDIUM → queued, LOW → daily digest) over a RabbitMQ event bus (`soc` vhost, reusing the live `opencti-rabbitmq` broker), writes metrics to InfluxDB (visualized by the already-provisioned Grafana `SOC Overview` dashboard) and to Elasticsearch (`soc-alerts-*`, drilled into via Kibana's `SOC Alert Investigation` saved-object dashboard), and fans out to LINE (HIGH) and Gmail API (MEDIUM immediate / LOW daily digest — switched from the diagrams' original Outlook/Microsoft Graph API choice; see `HANDOFF_OUTPUT_LAYER.md`'s "notification channel decision superseded" note for why). RabbitMQ/InfluxDB/Elasticsearch paths are live-verified end-to-end; the LINE/Gmail sends are dry-run-only. **The reason recorded here used to be "this sandbox lacks outbound internet" and that is wrong** — measured 2026-11-05, this machine resolves and completes TLS to `api.line.me` and `oauth2.googleapis.com`, and the live LINE token authenticates against the real Messaging API (channel "SOC Alert Lab" `@360hvcni`, quota `limited` 300/month, 0 used). LINE is dry-run **only** because `LINE_TO_ID` is empty, and that value cannot be obtained programmatically: `/v2/bot/followers/ids` returns HTTP 403 without a verified or premium Official Account, and a group/room id arrives only on a webhook event this project does not run. Gmail's OAuth2 credentials are deliberately left blank — see "Notifications & Output Layer" below.

Evaluation design includes a 4-way ablation (rule-based SIEM / ML-only / LLM-only / proposed hybrid) and an A/B analyst triage-time study (≥15 analysts × 20 alerts/group, blinded).

**Current implementation state:** the full data-prep chain exists as code and has been run end-to-end: `eda_sanity_check.py` → `preprocess_pipeline.py` → `label_builder.py` → `feature_extractor.py` → `build_cross_dataset_eval.py` (all in `src/`, see Commands below). The ML ensemble layer's three members are **all now trained** (CICIDS-2017 only in each case; UNSW-NB15 is left for the later cross-dataset stage): `notebooks/01_isolation_forest.ipynb` (Isolation Forest) — `models/isolation_forest.pkl` and its `reports/isolation_forest_*` outputs exist. `notebooks/02_random_forest.ipynb` (Random Forest) — `models/random_forest.pkl`, `reports/random_forest_val_metrics.csv`, `reports/random_forest_loao_results.csv`, and `data/features/cicids2017_rf_scores_val.parquet` all exist. `notebooks/03_autoencoder.ipynb` (Autoencoder, PyTorch, GPU-trained — see the CUDA note under Commands) has also been run — `models/autoencoder.pt`, `models/autoencoder_config.json`, `reports/autoencoder_val_metrics.csv`, `reports/autoencoder_loao_results.csv`, and `data/features/cicids2017_autoencoder_scores_val.parquet` all exist. See "Notebooks" under Commands below for each member's confirmed results. With all three members trained, `notebooks/04_fusion_layer.ipynb` (the Fusion Layer, original 80-feature-only design) is **fully written but not yet executed** — no cell outputs, no `models/fusion_layer.py`/`fusion_layer_config.json`, no `reports/ensemble_ablation_summary.csv`, no `data/features/cicids2017_fusion_scores_val.parquet` yet from that notebook specifically. **It has since been superseded by `notebooks/08_fusion_layer.ipynb`**, which has been run end-to-end: it fuses `models/random_forest.pkl` (80-feature, unchanged) with the Option A-adopted `models/isolation_forest_behavioral_v2.pkl`/`models/autoencoder_behavioral_v2.pt` (92-feature behavioral, joined via `orig_row_index`, not positional `row_index`) rather than the original `isolation_forest.pkl`/`autoencoder.pt`. This is now the real, current Fusion Layer — see "Notebooks (Fusion Layer, Option A integration)" below for its full design/results trail; `04_fusion_layer.ipynb` is kept only as a historical artifact of the pre-Option-A design, not something to run or extend. Note `08_fusion_layer.ipynb` belongs to the two-population design and is historical. Its `confidence_weighted` cascade was retired in favour of `rf_ae_or`, which has itself since been retired — the deployed strategy is `confidence_weighted` again, re-selected by nested LOAO on the unified population with different parameters (see "Fusion Layer" below). **Everything in this paragraph describes superseded populations**; the current state is the "Unified population" and "Fusion Layer" sections. **`enrich.py`, `alert_dispatcher.py`, the RAG layer, the LLM layer, SHAP, the synthetic overlay, and the rule-based SIEM baseline are all implemented now** — that sentence used to say they were design-stage only and is no longer true.

**`models/random_forest.pkl` is NOT in git.** It is 483 MB, over GitHub's 100 MB blob limit, and was removed from history in commit `6b8d648`; `.gitignore` now excludes it. The file exists locally. **A fresh clone has no Random Forest and must retrain it** by running `notebooks/02_random_forest.ipynb` before `src/evaluation/eval_test_set_ensemble.py` or `src/modeling/shap_explain.py` will work. Its hyperparameters and the metrics it must reproduce are tracked in `models/fusion_config.json` and `reports/random_forest_*.csv`.

**Operational hazard, learned the hard way (2026-10-25).** `data/` is gitignored, so a git worktree does not get it. Sharing it into a worktree with a Windows junction and later running `rm -rf` on the worktree **deletes through the junction and destroys the real `data/`**. This happened and cost a full pipeline rebuild. If you must share `data/` into a worktree, remove the junction with `rmdir` (never `rm -rf`), or better, have the script read an absolute path under `E:/thesis/data` instead of creating a junction at all. Everything lost was regenerable from `data/raw/` because every stage pins `random_state=42`; the rebuilt artifacts reproduced the originals exactly (row-hash join drift 0.00pp).

The repo is organized into domain packages under `src/`; invoke modules from the **repo root** with `python -m src.<package>.<module>` so package imports remain stable. Data/config paths remain root-relative.

- `src/` — all executable pipeline code, as domain packages (run each as `python -m src.<package>.<module>`): `ingestion/` (`preprocess_pipeline.py`, `synthetic_overlay.py`, `mitre_kb_extract.py`), `labeling/` (`label_builder.py`), `features/` (`feature_extractor.py`, plus the Option A behavioral pipeline run in this order: `behavioral_feature_extractor.py` → `validate_behavioral_join.py` → `feature_extractor_behavioral.py`; also `build_unified_population.py`), `modeling/` (`fusion_layer.py` — the deployed `confidence_weighted` cascade, see "Fusion Layer" below — `train_unified_ensemble.py`, and `shap_explain.py`), `evaluation/` (`eda_sanity_check.py`, `build_cross_dataset_eval.py`, `eval_test_set_ensemble.py`, `siem_baseline.py`, `baseline_model_comparison.py`, the `fusion_loao_*`/`fusion_or_sweep.py` LOAO scripts — `fusion_loao_unified.py` is the current one, `fusion_loao_trainnorm.py` the superseded two-feature-space predecessor — and the RAG/LLM evaluators), `rag/` (`rag_retrieval.py`, `rag_reindex_service.py`), `llm/` (`llm_explain.py`, `langchain_client.py`), `services/` (`enrich.py`), `notifications/` (`alert_dispatcher.py`, `notify_line.py`, `notify_gmail.py`, `config_utils.py`). `notebooks/01_isolation_forest.ipynb` builds and evaluates **only** the Isolation Forest ensemble member, on CICIDS-2017 (`data/features/cicids2017_features_{train,val,test}.parquet`); UNSW-NB15 and the Autoencoder/Random Forest members are left for later. Run it from within `notebooks/` (it resolves `ROOT` to the repo's parent directory) using the system/Anaconda Python kernel, not the `.venv` (see note above). Conventions established here that later ensemble notebooks should match:
- **Label/score remapping**: sklearn's `IsolationForest.predict` returns `-1`=anomaly/`1`=normal and `score_samples` is higher-is-more-normal — both are flipped once, explicitly, to the project-wide convention `1`=anomaly/`0`=normal and higher `anomaly_score`=more anomalous, since mismatched conventions across ensemble members would silently corrupt the later Fusion Layer.
- **CTI-encoded columns excluded from model input**: `technique_id_encoded`, `tactic_encoded`, `mapping_confidence_encoded`, `is_known_technique` are deterministic functions of the true `Label`/`attack_cat` (via `label_builder.py`'s static MITRE lookup), not real-world available at detection time — a first run of this notebook included them (84 features) and inflated every metric (e.g. AUC-ROC 0.8549 vs. the corrected 0.7286); they're reserved for the downstream LLM explanation layer, not any of the three detection models. `NON_FEATURE_COLS`/`select_feature_columns` in the notebook encode this exclusion — reuse the same list when building the Autoencoder/Random Forest notebooks.
- **Contamination tuning**: `contamination='auto'` hardcodes sklearn's decision threshold (`offset_ = -0.5`), unrelated to the data's actual anomaly rate — the notebook sweeps explicit values (`[0.05, 0.10, 0.15, 0.20]`) against validation F1 and found `0.2` best (F1 0.542 vs. 0.368 for `'auto'`); AUC-ROC is identical across all sweep values (confirmed via an in-notebook assertion) since contamination only moves the cutoff, not the tree-based ranking. The final saved model (`models/isolation_forest.pkl`) is refit with `contamination=0.2`.
- **Detection is heavily category-dependent**, not uniform: at the tuned threshold, per-category recall on the CICIDS-2017 val set ranges from 0.0 (FTP-Patator, SSH-Patator, Web Attack - Sql Injection, Web Attack - XSS) up to 1.0 (Heartbleed, n=2). Volumetric/flooding attacks (DoS Hulk, DDoS, DoS GoldenEye/Slowhttptest/slowloris) are caught reasonably well; low-and-slow / low-volume attacks (patator brute-forcers, PortScan, Bot, small web attacks) are essentially invisible to this unsupervised model regardless of threshold — expected to be exactly the gap the supervised Random Forest member and/or LLM layer need to cover.
- **LOAO (zero-day) evaluation** in §6 reuses `data/processed/loao/loao_{category}_{train,zeroday_test}.parquet` — these predate `feature_extractor.py` (78 raw unscaled CICFlowMeter columns only, no CTI columns, `Init_Win_bytes_forward/backward` still `-1`→`NaN`-sentineled), so each fold does its own train-only median imputation before fitting; tree-based Isolation Forest is scale-invariant, so training unscaled here isn't a methodological inconsistency with the scaled main-model run. Results per category are broadly consistent with the in-dataset per-category recall pattern above (e.g. DoS Hulk 0.90 recall vs. PortScan/FTP-Patator/SSH-Patator near 0).

**Option A (behavioral/time-windowed features) is adopted, with this exact scope — do not oversimplify this in future sessions.** A separate branch (`behavioral-time-windowed-features`) added per-source-IP time-windowed behavioral features (`conn_count`/`uniq_dport_count`/`fail_ratio`/`repeat_ratio` × 1/3/5-minute windows, 12 columns total) computed from the `GeneratedLabelledFlows/TrafficLabelling` raw distribution (see `src/features/behavioral_feature_extractor.py`), since the standard `MachineLearningCSV`-derived pipeline has no `Source IP`/`Timestamp` to compute them from. After a multi-phase validation (row-hash-join audit finding and fixing a dtype-mismatch false negative, then a properly pipeline-integrated retrain — see "Notebooks (behavioral feature engineering, Option A)" below for the full trail), the decision is: **the 92-feature behavioral set (78 raw CICFlowMeter + 2 sentinel-missing-flag + 12 behavioral) is now the standard input for Isolation Forest and Autoencoder going forward.** Random Forest was held out of this migration and kept on the original 80-feature capped-SMOTE set, on the stated grounds that behavioral features couldn't change its LOAO weakness because that weakness is a supervised-generalization limitation rather than a feature-representation one. **That claim has since been measured and is wrong** — see "Fusion Layer" and `reports/rf_behavioral_ablation_loao_report.txt`. It was reasoned from principle; RF had never actually been given the 12 columns. Given them, its nested zero-day recall goes 0.7942 → 0.9593 and its PortScan recall 0.075 → 0.831. The effect is not uniform, though: at argmax the behavioral columns *hurt* RF on DoS Slowhttptest (0.055 with vs 0.275 without) and DoS slowloris (0.224 vs 0.455), so report per category rather than claiming they help across the board. RF now trains on the same 94-feature unified matrix as the other two members.

The per-category nuance behind this decision, confirmed across three separate evaluations (an initial standalone/unvalidated prototype, then the properly Phase 1+2 pipeline-integrated retrain, then a LOAO re-run on that same integrated population) — report these per-category, not as a single blended "behavioral features help" claim:
- **DDoS**: a fully confirmed, robust zero-day recall gain for both Isolation Forest and Autoencoder, essentially unaffected by which population (unvalidated prototype vs. properly join-validated) trained the model.
- **PortScan, Autoencoder**: also a fully confirmed, robust zero-day gain (recall ~0.78 vs. a ~0.01 baseline), holding up almost exactly across both populations.
- **PortScan, Isolation Forest**: a *real* zero-day gain over the 80-feature baseline (0.002 → ~0.15 recall), but **substantially smaller than the unvalidated prototype's number suggested** (0.46) — more than halved once evaluated on the properly row-hash-join-validated population. Isolation Forest's PortScan zero-day detection is notably more sensitive to the exact BENIGN population used than Autoencoder's is; don't cite the prototype's 0.46 figure as current.
- **Bot, FTP-/SSH-Patator, Web Attack - Brute Force**: unchanged and still essentially undetectable zero-day (recall near 0) regardless of feature set, model, or which population was used. The original motivating hypothesis — that time-windowed behavioral features would specifically help catch low-and-slow brute-force-style attacks — is **not supported** by any of the three evaluations. This remains an open problem, not one Option A solves.

A necessary side effect of adopting the behavioral set: the row-hash join between the two independently-produced CICFlowMeter distributions could only match ~76.4% of BENIGN rows (100% of every attack category matched) — the unmatched ~23.6% of BENIGN is dropped and documented, not imputed or guessed. This shrinks Autoencoder's real BENIGN training population (960,726 vs. the original pipeline's 1,257,033) and is the leading explanation for the modest in-dataset F1 regression found in the properly-integrated retrain (0.889 vs. an unvalidated prototype's 0.914) — a cost that, per the per-category LOAO results above, mostly did *not* carry through to a zero-day-recall cost. Each retrained model's population size is also no longer row-for-row identical to Random Forest's — `orig_row_index` (added to the behavioral pipeline's output, threaded through Phase 1 and Phase 2) is the join key the Fusion Layer uses to align these models' scores against Random Forest's, instead of assuming positional `row_index` equality, which would silently misalign once row counts diverge. **The Fusion Layer migration itself (`models/isolation_forest_behavioral_v2.pkl`, `models/autoencoder_behavioral_v2.pt`, and the existing `models/random_forest.pkl`, joined via `orig_row_index`) is now done** — see `notebooks/08_fusion_layer.ipynb` and "Notebooks (Fusion Layer, Option A integration)" below.

### Unified population — the advisor's objection, fixed at the data layer

**Read this before citing any metric from `data/features/cicids2017_features_*` or `data/features/behavioral/cicids2017_behavioral_features_*`. Those populations are superseded.**

The thesis advisor rejected the fusion on the grounds that the supervised and unsupervised members were not on the same dataset, and the mechanism behind that objection was real: Random Forest read the `MachineLearningCSV`-derived matrix (80 features) while IF-v2 and AE-v2 read the `GeneratedLabelledFlows`-derived behavioral matrix (92 features). Those are two independent CICFlowMeter extractions of the same captures, so they could only be reconciled by `validate_behavioral_join.py`'s row-hash join, which matched 76.4% of BENIGN rows. The ensemble was therefore only evaluable on **80.36%** of the test split, and comparing it against an RF that saw 100% was never a fair comparison.

The fix was to stop joining, not to argue the join was good enough. `src/features/build_unified_population.py` splits 60/20/20 directly from `data/processed/behavioral/cicids2017_behavioral_labeled.parquet` (2,520,961 rows), which already carries every column all three members need. Result: **one population at 100% coverage, one 94-feature set (80 raw + 2 sentinel flags + 12 behavioral), one split, no join anywhere.** The five identifier columns (`Flow ID`, `Source IP`, `Destination IP`, `Timestamp`, `day_group`) are dropped from model input — `Source IP` in particular would let a model memorise which hosts attacked in this capture, which is leakage wearing a feature's clothes.

Pipeline on this population, in order:
```bash
python -m src.features.build_unified_population      # data/features/unified/, data/processed/unified_loao/
python -m src.modeling.train_unified_ensemble        # all three members, same features
python -m src.evaluation.fusion_loao_unified         # 10-fold LOAO, component scores + checkpoints
python -m src.evaluation.fusion_or_sweep --checkpoint-dir fusion_layer_loao_unified_checkpoints
```

**In-dataset val metrics** (`reports/unified_val_metrics.csv`): RF P 0.9996 / R 0.9997 / F1 **0.9997** / AUC 1.0000; IF F1 0.5670; AE P 0.9457 / R 0.8436 / F1 0.8918 / AUC 0.9792. Train-fitted normalization constants are in `reports/unified_norm_constants.json` (`if_max` 0.7170, **`ae_max` 0.0966**, fit on 1,780,362 train rows).

**Two things that are not good news and must not be smoothed over:**
1. **The old threshold 0.05 did not transfer, and re-selecting it changed the rule itself.** It was selected where `ae_max` was 0.1225; here it is 0.0966, so the same cut is looser. Re-selecting by nested LOAO on this population did not just move the number — `rf_ae_or` lost to both RF solo and the cascade, and the deployed rule changed. See "Fusion Layer".
2. **In-dataset metrics are saturated and cannot discriminate.** RF solo at F1 0.9997 beats the fused rule at every threshold tried. Differences of a few ten-thousandths prove nothing. Zero-day LOAO is the only evaluation in this thesis that separates the candidates.

M1c is **not** unblocked by this. CIC-UNSW-NB15's `Data.csv` carries no `Source IP` or `Timestamp`, so the 12 behavioral columns cannot be computed for it and the unsupervised members still cannot take part in cross-dataset evaluation.

### Supervised baseline comparison — why Random Forest, with evidence

`src/evaluation/baseline_model_comparison.py` answers the advisor's question "why these three models" by measuring the obvious alternative on the identical unified population, features and split. Previously that choice rested on convention; now it rests on a number.

| model | train | inference (504k rows) | precision | recall | F1 | AUC |
|---|---|---|---|---|---|---|
| **Random Forest** (sklearn, CPU) | 231.5s | 5.45s | 0.9996 | 0.9997 | **0.9997** | 1.0000 |
| XGBoost (GPU) | **38.7s** | **0.94s** | 0.9864 | 0.9950 | 0.9907 | 0.9961 |

XGBoost does not win on detection, and loses per-category recall nearly everywhere (Bot 0.931 vs 0.972, PortScan 0.986 vs 1.000, SSH-Patator 0.983 vs 1.000). But **it trains 6x faster and infers 5.8x faster**, and that belongs in the write-up next to the F1 column: scikit-learn has no GPU backend at all, so Random Forest is CPU-bound by the library, not by a configuration choice. What this run settles is only that no untested alternative is dramatically better — not that RF is optimal.

The per-category table carries an `n` column and flags every category with n < 100 as uninterpretable. Three qualify in val: Heartbleed (n=2), Infiltration (n=7), Web Attack - Sql Injection (n=4). XGBoost's 0.500 on Sql Injection is 2 rows out of 4, not a model weakness. One-Class SVM is deliberately **not** added: the unsupervised side already has its answer, since IF-v2 and AE-v2 correlate at 0.925-0.977 on per-category recall and the LOAO ablation already removed IF from the deployed decision.

### M1c cross-dataset generalizability — measured, and it collapses

`src/evaluation/eval_cross_dataset.py`. **Random Forest only, and that is a limitation rather than a choice**: the 12 behavioral columns derive from `Source IP`/`Timestamp`, which CIC-UNSW-NB15's `Data.csv` does not carry, so IF and AE cannot be scored on the target at all. This measures the supervised member in isolation and says **nothing** about the deployed cascade's generalizability — do not report it as an ensemble result. Binary attack-vs-benign on both sides, because the two attack taxonomies do not align (DoS Hulk is not Exploits) and a multi-class mapping does not exist.

**Three rows per direction, not two.** A cross-dataset score alone cannot distinguish "fails to generalize" from "the shared feature set is weaker", so each direction also trains a model on the shared columns and evaluates it in-dataset. That middle row is what makes the third interpretable.

| direction | model | evaluated on | n | precision | recall | F1 | AUC | FPR |
|---|---|---|---|---|---|---|---|---|
| cicids→unsw | CICIDS RF, full 80f | CICIDS test | 504,160 | 0.9957 | 0.9960 | 0.9958 | 0.9998 | 0.0009 |
| cicids→unsw | CICIDS RF, shared 76f | CICIDS test | 504,160 | 0.9944 | 0.9972 | 0.9958 | 0.9999 | 0.0011 |
| cicids→unsw | CICIDS RF, shared 76f | **UNSW test** | 61,235 | 1.0000 | **0.0003** | **0.0006** | **0.3220** | 0.0000 |
| unsw→cicids | UNSW RF, full 76f | UNSW test | 61,235 | 0.9283 | 0.9834 | 0.9551 | 0.9933 | 0.0274 |
| unsw→cicids | UNSW RF, shared 76f | UNSW test | 61,235 | 0.9283 | 0.9834 | 0.9551 | 0.9933 | 0.0274 |
| unsw→cicids | UNSW RF, shared 76f | **CICIDS test** | 504,160 | 0.1061 | **0.1229** | **0.1139** | 0.5034 | 0.2103 |

**The collapse is entirely generalization, not the feature reduction.** Dropping to the shared set costs −0.0001 F1 in one direction and exactly 0.0000 in the other. Without the middle row the whole drop could have been blamed on dropping four columns; it cannot.

**CICIDS→UNSW has AUC 0.3220, which is below 0.5 — the ranking is inverted.** That is stronger than failing to generalize: the model systematically scores UNSW's attack rows as *more benign* than its benign rows. Recall 0.0003 means it detects essentially nothing while its precision of 1.0000 is an artifact of firing almost never (it is a ratio over ~20 predictions). Quote recall and AUC, never that precision.

**UNSW→CICIDS is differently bad**: AUC 0.5034 is indistinguishable from random, with recall 0.1229 at FPR 0.2103 — it fires on a fifth of all benign traffic. So the failure is bidirectional but not symmetric: one direction inverts, the other is noise.

**The in-dataset reproduction is a control that passed**: CICIDS full-80f F1 **0.9958** matches the figure already recorded for `random_forest.pkl` exactly, confirming this pipeline measures the same thing the earlier work did.

**Two incidental findings worth keeping.** `Destination Port` — the feature SHAP ranks at the top for RF and which CLAUDE.md already flags as a possibly non-transferring dataset cue — is one of the four dropped columns, and removing it costs **nothing** in-dataset. It is prominent but redundant, not load-bearing. And prevalence differs between the two test sets (UNSW 26.51% attack, CICIDS 16.89%), so precision is not comparable across directions at face value; recall, FPR and AUC are.

**What this establishes.** The boundary of the single-dataset claim. These are two testbeds with different attack tooling captured years apart, and a model trained on one does not transfer to the other through shared CICFlowMeter statistics. That is a finding to report plainly, not a failed experiment — and it is the strongest available argument that in-dataset F1 near 0.9996 should not be read as a claim about deployment on new traffic.

### Fusion Layer — `confidence_weighted` is deployed; `rf_ae_or` is retired

**The deployed rule is an RF-primary cascade with an unsupervised fallback:**

```
rf_confidence = |rf_attack_probability - 0.5| * 2
fused_score   = rf_attack_probability     if rf_confidence >= 0.95
                (if_norm + ae_norm) / 2   otherwise
attack        = fused_score > 0.03
```

`src/modeling/fusion_layer.py` and `models/fusion_config.json` are the authority. All three
members contribute: RF owns the rows it is decisive about, and the two unsupervised detectors
decide the rest. `fuse_with_metadata` returns `model_used` as `random_forest` or
`if_ae_fallback` (`fusion_layer.MODEL_USED_VALUES`); `alert_dispatcher.derive_model_used`
duplicates that whitelist because the notification service must not import numpy, and
`tests/test_fusion_model_used_contract.py` fails if the two ever drift — renaming a branch
without migrating the consumer silently labels every affected alert `unknown`, which has
happened once already.

**Selected by nested LOAO on the unified population** (thresholds chosen on the other nine
categories, applied to the held-out one), `reports/fusion_layer_loao_unified_or_comparison.csv`:

| candidate | nested LOAO F1 | recall | FPR |
|---|---|---|---|
| **confidence_weighted** | **0.9782** | 0.9635 | 0.0007 |
| OR: RF>t1 or AE>t2 (2 thresholds) | 0.9745 | 0.9608 | 0.0011 |
| RF solo | 0.9737 | 0.9593 | 0.0011 |
| OR: max(RF, AE) (`rf_ae_or`, retired) | 0.9724 | 0.9559 | 0.0010 |
| AND: RF and AE | 0.9504 | 0.9062 | 0.0001 |
| AE solo | 0.8736 | 0.8176 | 0.0055 |
| IF solo | 0.4371 | 0.4502 | 0.0619 |

**This reverses the previous decision, and the reversal has a measured cause.** `rf_ae_or`
was chosen while RF was confined to the 80-feature `MachineLearningCSV` matrix and the
unsupervised members had the 92-feature behavioral one; there the OR beat RF solo by 9.3pp.
On the unified population all three share 94 features and the OR falls *below* RF solo.
`src/evaluation/rf_behavioral_ablation_loao.py` isolated why: dropping only the 12 behavioral
columns takes RF solo from nested F1 0.9737 to **0.8312**, landing on the old joined
population's 0.8327. The behavioral columns, not the population change, account for
essentially the whole gain, so **the old comparison was never fair to RF**.

**How much the ensemble actually buys, and where it loses.** On zero-day LOAO it is 0.45pp F1
over RF solo (0.9782 vs 0.9737) at better FPR (0.0007 vs 0.0011) — a real Pareto gain, but a
modest one. **In-dataset it is worse**: test F1 0.9966 vs RF solo's 0.9995, with FPR 0.000983
against 0.000093, a 10x difference (`src/evaluation/eval_test_set_ensemble.py`, n=504,193).
Do not quote the LOAO table alone; the honest claim is that the cascade trades in-dataset
precision for zero-day generalization, and on this dataset that trade is narrow enough that a
reader could reasonably prefer RF alone. **Never restate the old 9.3pp margin** — it describes
a configuration that no longer exists.

**Why the cascade's earlier dismissal no longer applies.** It was retired partly because its
own tuner chose `confidence_threshold=1.00` in 9/10 nested folds, switching the RF-primary
design off. On the unified population it chooses 0.95 in 9/10 folds (0.1 in the PortScan
fold), so the fallback genuinely carries undecided rows. This was checked before adopting it.
A side effect worth knowing: because the unified population gives IF and AE the same 94
features, the fallback averages two scores in one feature space — under the two-population
design it would have averaged across incompatible ones.

**Normalization constants are TRAIN-fitted and that is load-bearing.** Fit on
`data/features/unified/cicids2017_unified_train.parquet` (1,780,362 rows) with the deployed
models, `reports/unified_norm_constants.json`: `if_max` 0.7170, **`ae_max` 0.0966**. An
earlier revision carried val-fit constants with `AE_MAX = 0.811` against a true train-fit
0.1225 — 6.6x too large, which would shrink every deployed `ae_norm` by that factor and make
the threshold unreachable, silencing the detector with no error. Never substitute val- or
test-fit constants.

**Known limitations** (`models/fusion_config.json`): the in-dataset loss above; Bot nested
recall 0.000 (every member near-zero, so no combination rule recovers it); IF is the single
best zero-day detector on DoS Slowhttptest (argmax 0.839 vs AE 0.241, RF 0.055) yet carries
0.09–0.15 FPR in every fold, so excluding it as an independent trigger is a measured
trade-off rather than a free win; FTP-Patator and Web Attack - Brute Force have no redundancy
(both unsupervised members blind, recall ≤ 0.05) and PortScan is the mirror image (AE 0.785
vs RF 0.000 at argmax); in-dataset metrics are saturated (RF val F1 0.9997) and cannot
discriminate; normalized scores are intentionally unclipped so `fused_score` can exceed 1.0.

**Earlier LOAO reports were invalid and are preserved under explicit names.** They normalized
each fold's zero-day test scores with that same test fold's own min/max. See
`reports/*_legacy_test_fold_normalization.csv`. Correcting the bug moved every candidate
1–4pp but did not change their ranking.

`notebooks/08_fusion_layer.ipynb` and `src/evaluation/fusion_loao_trainnorm*.py` are
historical: they belong to the two-population design. Use `fusion_loao_unified.py` and
`fusion_or_sweep.py --checkpoint-dir fusion_layer_loao_unified_checkpoints`.

### SHAP explainability — migrated to the cascade

`src/modeling/shap_explain.py` attributes **the branch that actually decided each row**, in the units of the fused score, so `base_value + sum(shap)` reconstructs that row's `fused_score`:

- **`random_forest` rows** → `TreeExplainer` on `1 - P(BENIGN)`, which *is* the fused score on those rows.
- **`if_ae_fallback` rows** → `KernelExplainer` on the **composite** `(if_norm + ae_norm) / 2`, the quantity the cascade thresholds — not on one member of it.

**The unified population is what made the fallback attributable at all.** Under the retired `rf_ae_or` design, RF read 80 columns and the AE a separate 92-column matrix joined on `orig_row_index`; averaging two scores across incompatible feature spaces has no meaningful attribution, and `max()` has no single input space either. Now all three members read the same 94 columns, so the composite is an ordinary scalar function of one feature vector. This was a data-layer fix, not a code fix. A consequence: Isolation Forest genuinely influences fallback attributions, whereas the old module passed `np.zeros` in its place — correct then, fatal now.

**Faithfulness** (max `|base + sum(shap) − branch score|`): RF **1.96e-10**, fallback **4.66e-09**. Both are checked every run; if either were not tiny the attributions would be decoration.

**Measured latency**: RF **0.258 s/alert**, fallback **0.184 s**. The fallback being *cheaper* is the opposite of what the shapes suggest — KernelExplainer evaluates the composite over 500 coalitions against 100 background rows, running an IF pass and an AE forward pass each time, yet TreeExplainer over 200 trees × 15 classes still costs more. A hand-written claim in the report said the fallback dominated and was wrong on the first run, so that sentence is now derived from the measurement. RF is also much faster than the 1.03 s/alert recorded for the old 80-feature model. Both paths are usable per alert and impractical for bulk scoring.

**Branch mix, measured on a random 60,000-row slice of the unified test split: RF decisive 99.785%, fallback 0.215%.** The fallback is therefore sampled *deliberately* for the report — a random 60-row sample would contain none and that path would go unmeasured. The contrast is the substantive part: on the synthetic overlay (out-of-distribution input) RF abstained on **every** flow and the fallback decided 100% of alerts. The fallback exists for exactly that case, which is an argument for the cascade that the LOAO table does not show.

**Global importance now corroborates the ablation independently.** RF's top features are `uniq_dport_count_5m` (0.0517), `uniq_dport_count_3m` (0.0417), then `Destination Port` (0.0350) — behavioral columns dominate. Previously `Destination Port` topped RF's list, and it is still worth flagging as a dataset-specific cue that may not transfer. Two separate measurements — the LOAO feature ablation and this attribution — now agree that the behavioral columns are what drive RF. The fallback's list is led by `Init_Win_bytes_forward_missing` (0.0175) and `URG Flag Count` (0.0149), i.e. different features entirely, which is the point of attributing per branch.

Outputs `reports/shap_explainability_report.txt` and `reports/shap_global_importance.csv`. Caveats stated in the report: feature values are MinMax-scaled model inputs, not raw packet counts; global importance is a sample statistic (300 RF rows, 60 fallback rows) not a full-split one; and a high mean |SHAP| means a feature moves the score, not that it is causal.

### Rule-based SIEM baseline

`src/evaluation/siem_baseline.py` gives the 4-way ablation its missing floor. It now reads the **unified** population, so it is scored on the same test split as the ensemble it is compared against — it previously read the behavioral population while the ensemble had moved to the unified one, which made the headline comparison two different test sets reported as one.

On the unified test split (n=504,193): P 0.8297 / R 0.8980 / **F1 0.8625** / FPR 0.0375. On the same split the deployed cascade reaches F1 0.9966 (FPR 0.000983) and Random Forest alone F1 0.9995 (FPR 0.000093).

**The aggregate is misleading and must be reported per-category.** It is carried almost entirely by DDoS 0.988, DoS Hulk 0.983 and PortScan 0.933, while **8 of 14 categories score exactly 0.000** (Bot, FTP-/SSH-Patator, all three Web Attack types, Heartbleed, Infiltration) and two more are within rounding of it (DoS slowloris 0.006, DoS Slowhttptest 0.007). DoS GoldenEye manages 0.130.

Rules live in a `RULES` table, one row per rule; adding a rule is adding a row, never editing control flow. **Every threshold is a percentile of the train-BENIGN distribution**, never hand-written, because the features are MinMax-scaled. Three findings worth citing, all reproduced on the unified population: the port-scan rule **R1 fires on zero attack rows** while producing 4,240 false positives, so PortScan's 0.93 recall comes from the volume rule R3 instead; the brute-force rule **R2 catches DoS Hulk and DDoS rather than the Patators it targets** (target recall 0.000 against overall recall 0.630); and the beaconing rule R5 fires on nothing at all. Two rules were recorded as **not implementable** rather than faked: distributed credential stuffing needs per-destination aggregation across source IPs (every behavioral column is per source IP), and web-exploit signatures need payload inspection that CICFlowMeter flow statistics do not carry.

### Synthetic attack overlay and MTTD (M1b) — measured

`src/ingestion/synthetic_overlay.py` now targets the **unified** population, because the 92-column behavioral space it used to generate into is missing `Source Port` and `Protocol` and so could not be scored by the deployed models at all. It writes `data/synthetic/cicids2017_overlay.parquet`: 12,960 flows = **3.0000%** of the unified test BENIGN baseline (419,045), under the 5% ceiling enforced in code. Five classes in a `PROFILES` registry, deterministic under seed 42: brute_force 3,240, credential_stuffing 3,240, c2_beacon 2,592, port_scan 2,592, data_exfil 1,296, across 228 campaigns. Every row carries `inject_id`, a tz-aware `inject_timestamp`, `synthetic`, `attack_class`, `campaign_id`, and `Label="SYNTHETIC"`.

There is no saved raw counterpart to the unified splits, so the generator re-derives the `MinMaxScaler` from the same source with the same seed (read-only, importing `build_unified_population.split_population` so it cannot drift) and then **verifies** it against the pipeline's own scaled test parquet. Recovery error is ~2e-16, i.e. exact. `feature_columns()` now selects the 94 by exclusion rather than taking the first 92 positionally, which silently depended on the writer's column order.

**MTTD is measured** by `src/evaluation/mttd_eval.py`: it scores every injected flow with the three unified models, applies `fusion_layer.fuse`, and sets `detected_at = inject_timestamp + measured per-flow scoring latency` (23 µs, measured in-run). Transport, enrichment, RAG and LLM time are excluded deliberately — none is live-verified end to end, and all sit *after* the detection decision.

**The headline per-campaign MTTD is degenerate and must not be quoted.** It comes out at 0.0000 s because the first flow of all 228 campaigns is detected. The cause is identified, not guessed: a campaign's earliest flow carries an **all-zero behavioral vector** (physically correct — a source IP has no prior window activity), and the deployed rule scores those flows at a mean fused score of **8.94** against the 0.03 threshold, ~300x over. So that figure measures the generator's window initialization, not timeliness. Note the all-zero pattern is *not* itself anomalous in the real data (4.58% of real BENIGN test rows, 0.004% of attack rows), so the detection is not spurious — it is just free.

**Cite the de-artifacted variant instead** (`reports/mttd_metrics_excluding_first_flow.csv`), which drops each campaign's earliest flow and asks how long the campaign then runs unseen. It discriminates, and sensibly:

| attack class | campaigns | MTTD mean | median | max |
|---|---|---|---|---|
| port_scan | 4 | 0.00 s | 0.00 s | 0.01 s |
| credential_stuffing | 6 | 0.14 s | 0.15 s | 0.31 s |
| brute_force | 10 | 0.98 s | 0.53 s | 2.63 s |
| c2_beacon | 34 | **193.27 s** | 204.15 s | 482.94 s |
| data_exfil | 174 | **451.53 s** | 417.41 s | 888.97 s |

Burst classes are caught essentially immediately; the low-and-slow classes take 3–7 minutes, which is the expected and reportable shape. No campaign went undetected in either variant.

**A result about the cascade worth keeping:** **100% of alerting flows were decided by `if_ae_fallback`, zero by `random_forest`.** RF never reached confidence ≥ 0.95 on any synthetic flow, so the supervised member abstained on all of them and the unsupervised fallback carried the entire overlay. That is the fallback doing exactly the job it exists for on out-of-distribution input, and it is an argument for the cascade over RF solo that the LOAO table does not show.

**Do not read detection rates on this overlay as detection evidence**, and there is now a measured reason rather than only a caveat: the overlay's behavioral columns are far weaker than real traffic's — `conn_count_1m` tops out at **0.014** against **1.0** in the real unified test split, and `uniq_dport_count_1m` at 0.32 against 1.0. The synthetic port scan is much less aggressive than a real one on exactly the features Option A added. The report also states per column which are genuinely modelled, which derived, which heuristic, which placeholder. The real parquet has no timestamps, so anyone merging the overlay into a replay must assign benign times; `inject_timestamp` stays authoritative.

### OpenCTI enrichment service

`src/services/enrich.py` consumes `pa5220.raw`, enriches against OpenCTI, and publishes `pa5220.enriched` (the topic `observability/logstash/pipeline/soc.conf` already consumes). Enrichment is **additive**: the raw event is never mutated and no field dropped, because both topics land in Elasticsearch and must stay diffable. An unmatched event still carries `enrichment.matched: false`, so a consumer never has to distinguish "no enrichment ran" from "enrichment ran and found nothing". Offsets commit only after a successful publish. An OpenCTI failure still publishes, with `enrichment.error` — the pipeline losing enrichment is acceptable, the pipeline stopping is not. Bounded LRU+TTL cache with a circuit breaker. GraphQL goes through stdlib `urllib`, so `pycti` is not needed.

`uv run python -m src.services.enrich --dry-run` exercises the whole path against stubs, and **27 tests pass with no broker and no OpenCTI**. What is **not** verified: any real Kafka broker, any real OpenCTI, and the GraphQL query shapes, which were written from knowledge of 5.12.x and may need adjustment on first live contact (a wrong query degrades to "no match", not a wrong match). Live mode needs `kafka-python`, which is not installed.

### RAG Layer — knowledge base source decision (OpenCTI investigated, permanently not adopted)

`data/knowledge_base/mitre_techniques.json` (the Phase 1 knowledge base behind the RAG layer's approved 45-chunk design — 11 techniques, `T1046, T1059, T1071.001, T1110, T1110.001, T1190, T1210, T1498, T1499.002, T1505.003, T1595`) is sourced from a direct fetch of the raw `mitre-attack/attack-stix-data` GitHub STIX bundle (`enterprise-attack/enterprise-attack.json`, ATT&CK v19.1), **not** from OpenCTI, even though the architecture diagrams (formerly `diagrams/thesis_dataflow_v2.drawio`, now in `E:\thesis-doc\03_Diagrams\`) show OpenCTI → Vector DB. This was a deliberate choice, investigated thoroughly (2026-07-17) and closed permanently — do not re-open this question in a future session without new evidence (e.g. a confirmed OpenCTI upstream release that adds Detection Strategies support or fixes the dedup bug below).

**Why the GitHub-STIX source was kept instead of switching to OpenCTI's GraphQL API**, despite OpenCTI running locally (`opencti-connector-mitre-1`, healthy, already ingesting this same MITRE ATT&CK data) and being the architecturally "correct" source per the diagrams — live investigation against the running instance (platform + connector both pinned at `opencti/*:5.12.17` in `opencti/docker-compose.yml`) found two content gaps, both confirmed structural rather than simple version lag:

1. **Detection guidance is 100% absent, not just outdated.** `AttackPattern.x_mitre_detection` came back empty for all 11/11 target techniques — confirmed via the raw `toStix` STIX2 JSON (the key doesn't exist on the object at all), and a full introspection of the platform's 757 GraphQL types found zero types related to `DetectionStrategy`/`Analytic` (the newer ATT&CK data model that the original Phase 1 extraction had to reconstruct rich "Analytic NNNN: ..." detection text from, since it's no longer a flat STIX field). This isn't fixable by upgrading: the current **master** (unreleased) branch of `opencti/connector-mitre` still requires only `OpenCTI Platform >= 6.x` and its own entity-mapping table still has no `x-mitre-detection-strategy`/`x-mitre-analytic` row; Filigran's own OpenCTI v7.0 feature announcement (latest release checked, `7.260715.0`) makes no mention of Detection Strategies/Analytics anywhere; and **[opencti#11521](https://github.com/OpenCTI-Platform/opencti/issues/11521)** ("x-mitre-asset Not Supported – MITRE Connector Fails on ATT&CK v17.1 Import," opened June 2025, still open/unresolved) is direct, general evidence that OpenCTI's custom-STIX-type support lags MITRE's ATT&CK schema evolution as a pattern, not a one-off gap. Nobody has built this upstream yet, at any released version — this is a missing feature, not a config or version problem.
2. **Mitigation content gets corrupted by a platform-level entity-merge bug, not a connector quirk.** Querying `coursesOfAction` on Enterprise techniques returned ICS-domain mitigation IDs/text instead of the expected Enterprise ones (e.g. T1046 expected `M1030`/`M1031`/`M1042`; OpenCTI returned `M0930`/`M0931`/`M0942` with much shorter, generic ICS-style descriptions in place of the detailed Enterprise text). Pulling the merged entity's own external references confirmed the root cause: a single OpenCTI record carries **both** `attack.mitre.org/mitigations/M1030` and `attack.mitre.org/mitigations/M0930` as external refs, having kept only the ICS `x_mitre_id`/description. OpenCTI's own deduplication docs (checked against **current/latest** docs, describing 7.x behavior) still state Course-of-Action entities are matched by `("name" OR "alias") AND optional "x_mitre_id"` — an `OR name` rule that structurally allows same-named mitigations from different ATT&CK domains to merge. This is platform-level entity-resolution logic (applies "whether manually by a user or automatically by the connectors/workers chain" per OpenCTI's docs), not something a connector version bump touches. **[opencti#1026](https://github.com/OpenCTI-Platform/opencti/issues/1026)** ("Change the Attack Pattern / Courses Of Action standard IDs," closed/"Solved" in release **4.1.0, 2021**) shows OpenCTI attempted to fix exactly this class of ID-generation problem five years ago — yet the collision reproduces live on the current 5.12.17 instance, and the current docs describe the same name-matching rule as intended present-day behavior. No evidence of a fix for the cross-domain case was found in any changelog/issue search.

Given both gaps are architectural (missing feature; documented-as-intended dedup rule) rather than version lag, and the only upgrade path that touches either one is a full platform upgrade (`5.12.17` → current `7.260715.0`/LTS `7.260309.0-lts.6`, crossing OpenCTI's own versioning-scheme change from semver to calendar-versioning, i.e. at least two major-version generations) against a live instance with real ingested data across 9 running connectors — the risk/reward was judged not worth it for either issue, and neither has a safe isolated (connector-only) test path since both require the platform bump just to reach the code path that might matter. **Decision: keep the static GitHub-STIX snapshot as `mitre_techniques.json`'s source, permanently.** OpenCTI's role in this thesis stays as Output Layer infrastructure (Elasticsearch/RabbitMQ backend, see `observability/`) and a production-readiness demonstration — not the RAG knowledge base source. See `docs/handoffs/HANDOFF_RAG_PHASE3.md`'s addendum for the same record in the phase-brief file.

### Bringing up the infrastructure stacks

The shared Docker network must exist before any stack starts (only `network/docker-compose.network.yml` creates it as a named/non-external network the first time; other composes reference it as `external: true`):
```bash
docker network create soc_shared
docker compose -f network/docker-compose.network.yml up -d
docker compose --env-file opencti/.env -f opencti/docker-compose.yml up -d
docker compose --env-file observability/.env -f observability/docker-compose.yml up -d
docker compose --env-file notification/.env -f grafana/docker-compose.yml up -d
```
Each stack's `.env` file holds real credentials/tokens; never print or commit their contents. The Compose commands above name each stack's env file explicitly.

`observability/.env.example` lists the three required InfluxDB initialization keys. Add them with unique values to the ignored `observability/.env`; Compose exits if any are missing. `opencti/.env.example` lists the platform bootstrap token, the worker token, and one token variable per connector. OpenCTI 5.12.17 documents the worker token as requiring an administrator account with bypass capability, so provision a dedicated worker service identity with that required privilege and set `OPENCTI_WORKER_ADMIN_TOKEN`; do not reuse the platform bootstrap token. Create a separate least-privilege Connector-role account/token for each connector and set its matching `OPENCTI_*_CONNECTOR_TOKEN` variable. Only the platform receives `OPENCTI_ADMIN_TOKEN`. Compose fails closed until these credentials are provisioned in the ignored `opencti/.env`.

**Grafana admin credentials — resolved 2026-07-18, deliberate volume reset, user-authorized.** A prior session found the live Grafana instance's admin password wasn't the documented `admin`/`admin` default and wasn't recorded anywhere in this repo (see git history around 2026-07-18 for the original incident writeup if needed) — root-caused to the `grafana_grafana-data` volume (created 2026-05-04, predating the Dashboard & Notification Layer work) already holding a different, unrecovered password by the time anyone needed real API/UI access. **Before resetting anything, the volume's `grafana.db` was inspected read-only** (copied out via `docker cp` from the running container, queried directly with `sqlite3`/Python — no live credential needed for this, since it bypasses Grafana's own auth entirely): it held exactly 1 user (`admin`, no others), and every dashboard/folder/datasource present (`SOC Overview` dashboard + its `Thesis SOC` folder, `InfluxDB-SOC`/`Elasticsearch-SOC` datasources) was already file-provisioned from `grafana/dashboards/soc-overview.json` and `grafana/provisioning/{dashboards,datasources}/*.yml` — confirmed via the `dashboard_provisioning` table's recorded checksum against the actual on-disk file. Zero alert rules, annotations, API keys, snapshots, teams, or playlists existed. **Nothing of value would be lost by wiping the volume** — everything meaningful was already reproducible from files already in this repo.

Grafana now receives only the explicitly listed admin and datasource settings from `notification/.env`; the broad `env_file` injection is removed. Compose requires `GF_SECURITY_ADMIN_USER` and `GF_SECURITY_ADMIN_PASSWORD` plus the datasource settings, and has no vendor credential fallback. The current local Grafana password matches the vendor default and must be rotated to a unique password in the ignored `notification/.env` before startup; its value is not recorded here. Use `notification/grafana.env.example` as the key template. Compose interpolation does not rotate an already initialized Grafana database, so an existing volume may need an authenticated password change or a separately authorized reset.

Historical runtime verification on 2026-07-18 used the then-current local credentials and volume. It does not verify the current compose configuration or any later credential rotation; the Grafana host port is now limited to loopback.

## Working with the datasets

**Note on `eda_sanity_check.py` vs. `preprocess_pipeline.py` currently disagreeing about the UNSW source**: `eda_sanity_check.py` was not touched during the CIC-UNSW-NB15 migration and still loads/reports on the *old* raw UNSW-NB15 4-file format (`UNSW-NB15_1..4.csv`, still present in `data/raw/` but no longer used by `preprocess_pipeline.py`). Its UNSW-related findings below no longer describe what actually feeds the `unswnb15` pipeline slot — treat them as historical/archived, relevant only if `eda_sanity_check.py` is updated or the old format is ever revived.

Known quirks (already handled in `eda_sanity_check.py`, keep these in mind for any new preprocessing script):
- CICIDS-2017 column names have stray leading/trailing whitespace — must `.str.strip()` them.
- CICIDS-2017's public `MachineLearningCVE` distribution has no `Timestamp`/IP/port columns (stripped for privacy); only `GeneratedLabelledFlows` has real timestamps, needed later for simulated replay feeds.
- *(old raw UNSW-NB15 format, archived — see note above)* `NUSW-NB15_features.csv` (feature name reference) is `cp1252`-encoded, not UTF-8; the raw `UNSW-NB15_*.csv` data files have no header row, so column names must be assigned from that features file. `UNSW-NB15_1.csv` has a BOM; reading everything as `utf-8-sig` is safe.
- *(old raw UNSW-NB15 format, archived)* `attack_cat` and `Label` (binary) were two independently-sourced columns that had to be cross-checked for consistency (non-null/non-empty `attack_cat` should imply `Label == 1`). CIC-UNSW-NB15 doesn't have this problem — `preprocess_pipeline.py`'s `load_unsw()` derives both `attack_cat` and `Label` from the same `Label.csv` numeric code, so they're consistent by construction (`clean_unsw()` now just asserts this rather than reconciling two independent sources).
- Both datasets contain duplicate rows and out-of-range values (inf/-inf in CICIDS `Flow Bytes/s`-style rate columns); nothing is dropped/imputed/scaled in the sanity-check stage — that belongs in a separate future preprocessing script.
- CICIDS-2017 `Label` values like `Web Attack – Brute Force` are mojibake at the source (the dash was already corrupted to U+FFFD before distribution, confirmed via raw byte inspection — not a wrong-encoding-choice bug on our end). Read with `utf-8-sig` as usual; re-reading as `cp1252` makes it worse. `preprocess_pipeline.py` normalizes `–`/`—`/`�` to a plain `-` so labels are at least consistent enough to map to MITRE, but the original dash is not recoverable.
- CICIDS-2017's `Init_Win_bytes_forward`/`Init_Win_bytes_backward` use `-1` as a CICFlowMeter sentinel meaning "not measured," not bad data — convert to `NaN` for only these two columns rather than treating them with general negative-value cleaning, and never drop those rows (it would discard >1/3 of the data). CIC-UNSW-NB15's equivalent renamed columns have no such sentinel (confirmed empirically: min value 0, zero `-1`s), so no analogous handling was needed there.
- CIC-UNSW-NB15's `Data.csv` has substantial duplicate rows (141,742 of 447,915, ~31.6%) removed by the same `clean_common()` dedup step used for the other two datasets — unlike the CICIDS/old-UNSW sentinel columns, there's no NaN-preservation subtlety here, it's a plain full-row dedup.
